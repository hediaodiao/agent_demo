# 小红书 Agent 话术与追问应对（2026 版）

> 覆盖范围：小红书 Agent 开发 / Agent 服务端 / Agent 平台研发 一高频题
> 内容来源：小红书原帖在牛客网的转载 + CSDN 聚合整理（2026 最新一手面经）。
> 编写原则：以**生产级（非 demo）**标准作答，demo 里的妥协（如内存版 MemorySaver）一律标注「生产应替换为 X」。话术是骨架，面试时按自己真实项目替换占位符。

## 一、项目深挖（占比最大，照简历拷打）

### Q1. 讲一下你这个项目在公司处于什么位置？上下游是什么？架构与价值？
**话术**：
"我负责的 Agent 是【业务域】里的【角色】，上游是【数据/需求来源，如工单系统、文档库、用户请求】，下游对接【执行系统，如 API、数据库、消息队列】。整体架构分四层：接入层（协议适配 + 鉴权）→ 编排层（Planner/Executor/Critic）→ 能力层（Tool/MCP/检索）→ 存储层（记忆 + 知识库）。它解决的核心痛点是【手动流程慢 / 跨系统跳转多 / 非结构化难处理】，上线后把【某指标】从【X】提升到【Y】，人均节省【Z】工时。"

**追问应对**：
- 追问"上下游再细一点"→ 用具体数据流串一遍：请求进来→哪个模块校验→调了哪几个工具→结果写到哪。
- 追问"为什么是你做而不是用现成 SaaS"→ 强调数据不出域/私有协议/合规要求，这是自研的真实理由。

### Q2. 效果/质量指标怎么评定？从 65% 提升到 90% 怎么算的？
**话术**：
"我们建立了离线评测集：固定【N】条真实任务 + 标准答案，用【准确率/任务完成率/人工打分（LLM-as-Judge）/ RAGAS】多维度评估。65%→90% 不是模型自己说的，是评测集上跑出来的：基线 Prompt 直连模型 65%，加入【规划链路 + 检索重排 + 反思重试】后到 82%，再补【工具调用校验 + 失败兜底】到 90%。每次改动都跑回归，避免凭感觉。"

**追问应对**：
- 追问"评测集怎么来的、会不会过拟合"→ 说明评测集来自真实线上抽样 + 持续追加 bad case，定期刷新，且留 20% 作为盲测集不上训练。
- 追问"90% 还差 10% 是什么"→ 诚实说长尾：多跳推理失败、权限边界 case、工具超时，已在排期。

### Q3. 文档/数据规模多大？面对公司级超大文档库怎么扩展？
**话术**：
"当前是【X 万】篇，已在用【分层索引 + 异步入库】。扩展到十万/百万级：① 入库走消息队列削峰，切块用标题感知 + 结构感知；② 检索用 IVF-PQ/HNSW 分级（热数据 HNSW、冷数据 IVF-PQ）；③ 加**混合检索**（BM25 + 向量）+ 重排；④ 缓存高频 Query 结果；⑤ 用列式/分层存储控制成本。"

**追问应对**：追问"索引重建要多久、影响线上吗"→ 答双索引热切换：新索引建完再切流量，旧索引保留回滚。

### Q4. Agent 推理逻辑可解释吗？给谁看？看到后做了什么优化？
**话术**：
"可解释性分两层：给**开发者**的是 Trace（每步 Plan/Thought/Tool/Result 全链路，带 TraceID，可观测）；给**用户**的是精简推理摘要（折叠展示）。看到推理过程后做的优化：① 发现子 Agent 重复检索→加结果缓存；② 发现规划跑偏→加 Critic 预算截断；③ 发现工具参数错→加 Schema 校验前置。"

**追问应对**：追问"用户看推理会不会泄露内部逻辑"→ 答按角色脱敏，用户侧只给结论级摘要，敏感步骤折叠。

### Q5. 实习指标/业务上下游/代码框架（被狂追问）
**话术**：
"实习聚焦【指标名，如自动化率/首响时长】，基线【X】，我做的【动作】把它做到【Y】，相对提升【Z%】。代码框架是【FastAPI/Spring + LangGraph/自研状态机】，工具用【MCP/Function Calling】接入，记忆用【Redis + 向量库】。上下游：左接【数据源】，右接【执行端】。"

**追问应对**：任何数字都要能解释口径。"这个 30% 提升是同一评测集前后对比，不是不同样本"——务必把口径说死。

## 二、Agent 架构与核心概念

### Q6. 为什么做多 Agent 而不是一个 Agent 塞满能力？
**话术**：
"单 Agent 在长链路里会出现**上下文污染、错误放大、调试困难、职责不清**。多 Agent 把角色显式化：Planner 规划、Retriever 检索、Executor 执行、Critic 审查。但多 Agent 不是银弹——任务可分阶段、子任务边界清晰、单 Agent 已明显退化时才上。我们只在【具体场景】拆了【N】个子 Agent，其余仍单 Agent，避免过度拆分带来调度开销。"

**追问应对**：
- 追问"拆多了怎么办"→ 答用主 Agent 做路由/编排，子 Agent 无状态或短状态，控制跳数（如 ≤5）。
- 追问"怎么判断该不该拆"→ 答看三点：链路长度、是否跨异构数据源、是否需不同权限/模型。

### Q7. 主/子 Agent 信息怎么交互？子 Agent 返回什么？主 Agent 感知失败/超时/重试吗？
**话术**：
"交互走结构化消息：主 Agent 下发【目标 + 上下文摘要 + 约束】，子 Agent 返回【结果 + 状态（success/fail/partial）+ 关键证据 + 需要的后续依赖】。**不返回**原始长上下文，只回精炼结论，避免主 Agent 上下文膨胀。主 Agent **必须感知**失败/超时/重试：超时走熔断 + 降级（换模型/换工具/人工接管），失败带错误信息回 Critic 决定重试或换路。"

**追问应对**：追问"超时阈值怎么定"→ 答按工具 P99 延迟 + 业务容忍度设，配指数退避；追问"重试幂等"→ 写操作带幂等键，只读可随意重试。

### Q8. MCP / Function Calling / Skills / Agent 关系？
**话术**（标准答法）：
"四者在不同层次：
- **Function Calling**：模型输出结构化调用意图的接口能力（'调什么、传什么参'），是模型侧能力。
- **MCP（Model Context Protocol）**：标准化工具/数据源接入协议，解决'接得规范'——统一 stdio/SSE/HTTP 传输与工具描述格式。
- **Skills**：封装好的可复用能力单元（如'查工单''检索日志'），是能力侧复用。
- **Agent**：围绕目标做规划、调能力、处理反馈、迭代执行的调度主体。
一句话：MCP 负责接得规范，Function Calling 负责调得出来，Skills 负责能力可复用，Agent 负责把能力组合成任务闭环。"

**追问应对**：追问"MCP 和 Function Calling 重复吗"→ 答不重复：FC 是模型表达意图，MCP 是工具侧通信标准；FC 的参数可映射到 MCP 的 tool 调用。

### Q9. Agent 规划/执行/反思三段式怎么设计？ReAct 流程？Planner/Executor/Critic？
**话术**：
"采用 Plan-Act-Reflect（与 ReAct 同源并补反思闭环）：
- **规划 Planner**：把目标拆成带【工具、输入依赖、终止条件】的可执行步骤，显式化。
- **执行 Executor**：严格按步推进，记录中间状态与工具返回，减少隐式假设。
- **反思 Critic**：基于轨迹检查目标完成度、证据充分性、有无漏调用/冲突规则。
**必须设预算**：最大重试轮数、回滚条件、人工接管阈值，防止无限循环把成本烧穿。Critic 不是替代 ReAct，而是在 ReAct 循环外加一层'该不该继续'的闸门。"

**追问应对**：
- 追问"为什么不用纯 ReAct"→ 答纯 ReAct 容易在错误路径上一直 Reason+Act 空转，Critic 用独立预算/独立模型做'止损判断'。
- 追问"Planner 不准怎么办"→ 答 Plan-and-Execute：先出计划再执行，执行中允许局部重规划，但总步数受控。

### Q10. 记忆架构：长时/短时记忆底层实现？怎么分层？
**话术**：
"三层：
1. **短期工作记忆**：当前任务的中间状态、已调工具、步骤完成度 → 用会话上下文 + 结构化状态对象（内存/Redis，TTL 过期）。
2. **长期用户记忆**：偏好、习惯、稳定背景 → 向量库 + KV 存储，按 user_id 索引，写入需去噪。
3. **外部事实记忆**：知识库/文档/事件流 → 向量检索 + 元数据过滤，可追溯。
**不能只靠聊天历史**：长上下文混入无关内容会污染判断，且成本高；必须把'会话痕迹'与'事实知识'分离，防止错误推断沉淀成长期污染。"

**追问应对**：
- 追问"生产级记忆用什么存储"→ 答：**短期用 Redis（带 TTL）；长期用户画像用向量库（如 Milvus/Qdrant）+ 关系型 KV；事实记忆用混合检索**。demo 里用内存版 MemorySaver 仅作演示，**生产必须替换为持久化 + 隔离 + 清理策略**。
- 追问"记忆怎么更新/遗忘"→ 答重要度打分 + 最近访问衰减 + 容量上限淘汰（LRU）；用户明确纠正时即时写。

### Q11. 上下文管理：上下文怎么做的、是否拆分？为什么现在都增大窗口不做压缩？
**话术**：
"我们做**选择性保留 + 摘要压缩**结合：保留关键决策节点和工具结果，历史用模型做摘要；超长会话按【滑动窗口 + 摘要】降噪。关于趋势：增大上下文窗口是主流，因为压缩会丢信息、且长上下文模型推理更强；但我们仍保留压缩作为**成本兜底**——不是替代长窗口，而是当超过经济阈值时降级用。"

**追问应对**：追问"压缩丢信息怎么补"→ 答关键事实不入压缩区，单独存结构化状态；追问"窗口多大算经济"→ 答按 token 成本 vs 准确率权衡，设业务阈值。

### Q12. Harness 怎么理解？OpenManus 用的什么框架？
**话术**：
"**Harness** 指把 LLM 包成可运行 Agent 的'外壳/运行框架'：负责调度循环、工具分发、状态管理、错误处理、可观测，模型只是其中一环。OpenManus 类项目通常用**自研轻量循环 + 工具注册表**，也有基于 LangGraph/CrewAI 的。我们选【X】是因为【可控性/状态机显式/并发模型】契合业务。"

**追问应对**：追问"Harness 和 LangChain 区别"→ 答 LangChain 是组件库+链，Harness 更强调'运行时的循环与治理'；很多生产 Agent 是自研 Harness 而非纯 LangChain。

## 三、RAG 与向量检索

### Q13. RAG 怎么分类？Agentic RAG 和传统 RAG 差别？
**话术**：
"传统 RAG 是检索→拼接→生成的固定管道。Agentic RAG 把检索变成 Agent 的可调用步骤：按需检索、多轮检索、根据中间结果决定**是否再查/查哪/用什么重排**。差别：传统 RAG 检索一次性，Agentic RAG 检索是'决策过程'，适合多跳、需迭代的问题。"

**追问应对**：追问"什么时候上 Agentic RAG 不值"→ 答单跳问答上 Agentic 反而增成本延迟，只有多跳/需反思时才划算。

### Q14. 怎么做召回闭环让系统越用越准？
**话术**：
"闭环四步：① 线上埋点记录每次检索的 Query/召回/用户反馈（点赞、采纳、纠正）；② 用反馈做难负例挖掘 + 评测集扩充；③ 定期重训/调重排权重、补 chunk 切分策略；④ 跑回归评测确认不退化。本质是'反馈→评测→优化→回归'的飞轮。"

**追问应对**：追问"没反馈信号怎么办"→ 答用 LLM-as-Judge 给伪信号 + 人工抽样校准，避免无监督漂移。

### Q15. HyDE 原理？什么时候有效、什么时候坑人？
**话术**：
"**HyDE**：先用模型对 Query 生成一篇'假设性答案文档'，再用这篇文档的向量去检索，因为假设答案的语义分布更接近真实文档。有效场景：Query 短、抽象、用户意图隐含。坑人场景：① 事实性强的精确检索（假设文档会引入幻觉向量，反而带偏）；② 多跳问题假设答案易错；③ 召回被'像答案'的噪声文档干扰。"

**追问应对**：追问"HyDE 和重排怎么配合"→ 答 HyDE 用于粗召回扩召回率，重排（Cross-Encoder）用于精排控准确率，二者互补。

### Q16. IVF / PQ / IVF-PQ 分别在做什么？向量索引类别与场景？
**话术**：
"- **IVF（倒排）**：用聚类把向量空间分成很多桶，检索只查最近的几个桶，减少计算量。
- **PQ（乘积量化）**：把高维向量切成多段分别量化压缩，大幅省内存，检索用近似距离。
- **IVF-PQ**：聚类 + 量化结合，又快又省内存，适合超大规模。
- 索引选型：**HNSW** 召回质量高、查询快但内存大，适合中小规模热数据；**IVF-PQ** 内存友好，适合亿级冷数据；**Flat** 精确但慢，只做小库基线。"

**追问应对**：追问"IVF 桶数怎么定"→ 答经验 √(N) 量级起，按召回率/延迟调；追问"PQ 段数影响"→ 段越多压缩越狠、精度越降，需 trade-off。

## 四、后端工程与协议（服务端方向）

### Q17. SSE 和 Streamable HTTP 的区别？
**话术**：
"- **SSE（Server-Sent Events）**：基于 HTTP 长连接单向流式推送，服务端→客户端，简单、浏览器原生支持，但只能单向、且长连接占用资源。
- **Streamable HTTP**（如 MCP 的 streamable-http）：在普通 HTTP 上支持流式响应（chunked / 可升级），更灵活，可双向、可复用连接、更好适配网关/负载均衡。MCP 推荐 streamable-http 替代旧 SSE 传输，主要解决 SSE 的连接管理与可扩展性短板。"

**追问应对**：追问"什么时候还用 SSE"→ 答纯下推、无复杂双向交互、要兼容老浏览器时 SSE 够用；需要断线重连/状态/双向则用 streamable-http。

### Q18. 如何适配 stdio / HTTP / SSE / Streamable HTTP 多种传输？
**话术**：
"抽象一层**传输适配层（Transport Adapter）**：定义统一的 `send/receive/close` 接口，每种传输实现对应 Adapter——stdio 走子进程 stdin/stdout；HTTP 走 request/response；SSE 走长连接读流；streamable-http 走可流式 HTTP。上层编排不感知传输差异，只调统一接口。这是 MCP 客户端的标准做法：Client 持 Transport，Server 同理。"

**追问应对**：追问"stdio 的进程怎么管理"→ 答连接池 + 健康检查 + 崩溃重启 + 超时回收，避免僵尸进程。

### Q19. 如何处理 MCP 版本兼容问题？
**话术**：
"三板斧：① **协议协商**：连接时交换版本号，按能力降级（老 Server 不支的特性客户端走兼容路径）；② **Schema 版本化**：tool 描述/参数带 version，客户端按 version 选解析逻辑；③ **灰度 + 回归**：新版本先小流量，跑 MCP 兼容性回归测试集。生产上不硬升，做向后兼容的中间层。"

**追问应对**：追问"Server 升级客户端不升怎么办"→ 答 Server 保留旧版能力一段时间（双版本共存），客户端按协商结果选。

### Q20. Java 后端实现 Agent 引擎调度，大量并发怎么处理？多线程并发冲突？
**话术**：
"并发模型：IO 密集（调模型/工具）用**虚拟线程（Project Loom）/ 线程池 + 异步**，避免阻塞；每个会话一个独立上下文（隔离），共享状态用**不可变对象 + 并发安全容器（ConcurrentHashMap）/ 原子类**。调度用状态机 + 事件队列，避免共享可变状态竞争。工具调用带超时 + 信号量限流，防雪崩。"

**追问应对**：追问"虚拟线程踩过坑吗"→ 答 synchronized 在虚拟线程下会 pin 载体线程，改用 ReentrantLock / 无锁结构；追问"上下文隔离"→ 答 per-session state，不用 static 可变。

### Q21. Java 类加载机制 / Redis 数据结构及底层？
**话术（类加载）**：
"双亲委派：加载请求先委派父加载器，父找不到才自己加载，保证核心类不被篡改、避免重复加载。破坏双亲委派的场景：SPI（JDBC）、热部署、模块化。
**话术（Redis）**：String（SDS）、Hash（ziplist→listpack/hashtable）、List（quicklist）、Set（intset/hashtable）、ZSet（跳表 + 字典）。用 ZSet 做延迟队列/排行榜，Hash 存对象，Bitmap 做布隆过滤。"

**追问应对**：追问"ZSet 跳表层数"→ 答随机层数（幂次概率），平均 O(log n)；追问"大 Key 怎么治"→ 答拆分 + 分批 + 异步删除。

### Q22. 场景题：对话 Agent 的会话表/消息表字段怎么设计？
**话术**：
"**会话表 session**：id、user_id、title、model、status、create/update_time、metadata（业务标签）。
**消息表 message**：id、session_id、role（user/assistant/system/tool）、content、tokens、tool_calls（JSON）、trace_id、parent_id（多轮/分支）、create_time。
要点：消息表按 session_id 分区；工具消息单独存 tool_result 便于审计；长上下文用摘要表单独存，主表只留最近 N 条 + 摘要指针。"

**追问应对**：追问"多轮分支（如重新生成）怎么存"→ 答用 parent_id 树形存，前端选分支；追问"成本统计"→ 答 message 表记 tokens，按 session 聚合算账单。

### Q23. AI 服务部署后怎么看稳定性？
**话术**：
"可观测三件套：① **Trace**（每步 Plan/Tool/LLM 调用带 TraceID，链路可见）；② **Metrics**（成功率、P99 延迟、Token 成本、工具错误率、重试率）；③ **日志**（结构化 + 脱敏）。再配告警（错误率/成本突增）+ 兜底（降级模型、限流、人工接管）。生产用 OpenTelemetry + Prometheus/Grafana。"

**追问应对**：追问"模型挂了怎么兜底"→ 答多供应商故障转移 + 缓存兜底答案 + 明确告知用户降级。

## 五、模型、稳定性与安全生产

### Q24. Agent 背后多模型还是单模型？模型网关自研还是第三方？
**话术**：
"生产用**多模型网关**：按任务路由（简单分类用小模型、复杂规划用大模型、代码用专用模型），做成本/质量权衡。网关我们【自研/用第三方如 LiteLLM】——自研可控路由+限流+审计，第三方省运维。核心是统一接口，模型可热插拔。"

**追问应对**：追问"怎么选模型"→ 答评测集上跑分 + 成本，路由规则可配置；追问"网关挂了"→ 答客户端本地兜底配置（直连主模型）。

### Q25. 稳定性做了什么（防幻觉/防死循环/兜底）？
**话术**：
"- **防幻觉**：检索增强 + 答案引用溯源（带出处）+ 事实一致性校验（LLM-as-Judge 查有无依据）。
- **防死循环**：Critic 预算（最大步数/最大重试）+ 状态去重（同样 (state,action) 不重复）+ 超时熔断。
- **兜底**：工具失败降级、模型故障转移、超预算转人工、敏感操作 human-in-the-loop。"

**追问应对**：追问"循环还没停就超成本了"→ 答硬上限（token 预算）+ 异步中断，成本优先于完成。

### Q26. 安全：Tool Injection 怎么防范？工具权限隔离？
**话术**：
"**权限过滤必须在检索/数据访问层完成，不能依赖模型自己遵守提示词。** 具体：① 工具按最小权限授权，每个工具声明可访问资源白名单；② 外部内容（检索结果/网页）视为不可信，做输入净化 + 隔离执行；③ 写操作/高风险操作必须 human-in-the-loop 或幂等键；④ 提示注入检测（识别'忽略之前指令'类）；⑤ 全链路审计日志。"

**追问应对**：追问"模型被诱导调了不该调的工具"→ 答工具层二次鉴权（调用时再验用户权限），不只靠模型判断；追问"隔离执行"→ 答工具在沙箱/独立上下文跑，结果回传前脱敏。

## 六、手撕代码 + 场景题

### Q27. 手撕：最长递增子序列（LIS）
**话术（思路先讲再写）**：
"两种：O(n²) DP（dp[i]=以 i 结尾的 LIS 长度）；O(n log n) 用**贪心 + 二分**（维护 tails 数组，对每个数二分找插入位）。面试优先讲 O(n log n)，再补边界。生产里这类'最优子结构'思路也用于 Agent 的规划剪枝。"

**追问应对**：追问"要输出序列还是长度"→ 答长度用 tails 长度即可；要序列需额外记录前驱。写时先说复杂度再写，别闷头写。

### Q28. 场景题：Agent 自我迭代广告投放最优并执行，怎么设计？
**话术**：
"四层：① **观测**：拉投放数据（CTR/CVR/ROI）+ 环境状态；② **决策**：Planner 基于指标生成候选策略（调价/换素材/换人群）；③ **执行**：在**小流量灰度**调工具执行，不直冲全量；④ **评估**：用对照实验（A/B）判优劣，胜出策略放大，失败回滚。关键约束：**自动迭代只在低风险动作上全自主，预算/策略大改必须人工审批**，且全程可观测可回滚。"

**追问应对**：追问"怎么防它越跑越偏"→ 答预算 + 收益阈值 + 人工兜底 + 异常自动暂停；追问"评估指标被污染"→ 答独立对照桶，不拿实验桶当真值。

### Q29. 场景题：从零设计对话 Agent / 企业知识库 / 多 Agent 编排
**话术（通用框架）**：
"按六步答：① 需求澄清（用户是谁、SLA、合规）；② 能力拆解（Plan/Tools/Memory 边界）；③ 数据流图（请求→检索→规划→执行→生成）；④ 模块时序（含失败分支）；⑤ 容量/降级/灰度（并发、成本、熔断）；⑥ 成本-效果折衷。企业知识库补：标题感知切块 + 混合检索 + 重排 + 权限过滤 + 引用溯源。多 Agent 补：主 Agent 路由 + 子 Agent 无状态 + 预算止损。"

**追问应对**：任何场景题被追问细节，回到"可观测 + 可回滚 + 最小权限 + 评测闭环"四原则，这是区分 demo 与生产的分水岭。
