## Q1. 【对应 HTML 问题 09】多 Agent 真正成立的价值为什么只有「并行」和「隔离」两点？阿姆达尔定律是什么？

**A：** Cognition（Devin 团队）《Don't Build Multi-Agents》的结论是：多 Agent 听起来高级，实战里更脆弱、更容易错（决策分散 + 上下文难共享）。所以默认单 Agent，只在"任务形状明确需要"时才拆。真正成立的拆法只有两点：

- **① 并行**：仅限"互相独立 + 只读"的任务（如同时查 5 个资料源）。有先后依赖或会改状态的不能并行。收益受**阿姆达尔定律**卡上限。
  - **阿姆达尔定律**：任务总提速上限取决于"可并行比例"和"并行单元数"。直觉是：一个任务哪怕 90% 能并行、10% 必须串行（启动、汇总躲不开），用 100 个 Agent 也最多快 ~10 倍；若只有 50% 能并行，无限并行最多快 2 倍。真实任务能干净并行的部分不多，所以**并行收益有限**。
- **② 隔离**：刻意让某些上下文不互通。典型场景：批评者看不到作者的私密推理，只给最终成品/结论。
  - **为什么**：若批评者能看到作者中间"偷懒、跳步、自我说服"的推理，会被带跑、顺着作者思路走，最后变成**橡皮图章**（不认真看、敷衍点赞）式通过，挑不出真问题。隔离草稿纸，批评者才必须独立判断"结论站不站得住"。
  - 类比：阅卷老师不该看到考生草稿纸——看了会被"我当时是这么想的"带偏而心软。

> **一句话**：并行 = 互不依赖的只读任务同时干，但提速有上限；隔离 = 故意不给某些 Agent 互通上下文（如批评者看不到作者推理），保住批评的独立性和锋利度。两者都是"默认单 Agent 不行时"的例外，不是炫技。

## Q2. 【对应 HTML 问题 09 延伸 · 上下文窗口概念】上下文窗口是单轮对话，还是多个会话各算一个？

**A：** 都不是单轮。准确说：**上下文窗口 = 当前这一个会话从开头到现在的全部内容**，模型每次回复都把整个会话重新读一遍再生成。

- 模型没有"上一轮说了啥"的记忆——记忆就是上下文里拼着的内容。一个会话聊 100 轮，第 101 轮看到的上下文就是前 100 轮 + 最新一轮。
- **不同会话是隔离的**：会话 A 和会话 B 互不可见，开新会话模型完全不知道你以前说过什么。所以"每个会话 = 一份独立上下文"理解正确。
- **豆包等聊天 App**：同一窗口内一直累积，开新对话清零；接近窗口上限时最早消息被截断/压缩（这就是"短期记忆退化，要摘要压缩"）。
- **跨会话记住东西靠的是长期记忆 / RAG**：不是上下文窗口本身。比如"记得你喜欢喝咖啡"，是因为存进了外部库，新会话再调出来。

> **一句话**：上下文窗口绑定单个会话（从开头到现在的全部内容），不是单轮；不同会话互不相通；跨会话记忆靠长期存储，不是窗口本身。

## Q3. 【对应 HTML 问题 10】程序性记忆是什么？用户上传的 Skill 算程序性记忆吗？

**A：** 程序性记忆是长期记忆三类之一（借用心理学分类）：

| 类型 | 人脑 | Agent 里 |
|---|---|---|
| 情景记忆 | 昨天发生了啥 | 对话历史 → 向量库，按语义找回 |
| 语义记忆 | 你是谁 / 你偏好啥 | 用户事实 / 偏好 → 知识图谱 / 结构化库 |
| **程序性记忆** | **怎么干活的肌肉记忆** | **Skills / 工作流模板（CLAUDE.md、系统提示里的固定流程）** |

- 程序性记忆 = **「怎么做事」的技能/流程**，开机即加载、永远生效，不靠"回忆某次对话"。典型载体：`CLAUDE.md`（行为规则如"提交前先跑测试"）、Skill 技能包（翻译润色模板、部署步骤清单）、固定工作流。
- **用户上传的 Skill 就是程序性记忆**（最典型例子）。它不依赖某次对话（非情景）、不是关于你的偏好事实（非语义），而是一套可复用操作流程——完全符合定义。对应伪代码 `self.skills = load("CLAUDE.md")`。
- **易混点：Skill vs RAG**：Skill 是 Agent"自己该怎么做"的模板，主动加载（能力/流程）；RAG 是"去查什么资料"，临时检索（信息/证据）。**Skill = 我会什么本事，RAG = 我去查什么资料**。

> **一句话**：程序性记忆 = Agent 怎么干活的固定技能/流程模板（CLAUDE.md、固定流程、用户上传的 Skill 都算），开机加载、跨会话生效，是"能力"不是"信息"。

## Q4. 【对应 HTML 问题 11】RAG 被工具化是不是就是 Agentic RAG？普通 RAG 就是没和 Agent 结合的硬编码吗？

**A：**
- **"RAG 被工具化 = Agentic RAG"，对，同一件事。** 把检索变成 Agent 手里的工具，模型自己决定何时查、查几次、怎么改写 query，就是 Agentic RAG 的定义。日常说"Agent 的 RAG"基本就是 Agentic RAG。
- **普通 RAG 不是"硬编码"，而是"固定管线 / 被动响应"**——检索时机、次数、query 都写死在代码里：问一次→查一次→答一次。模型没有决策权，不能"查完不够再补查"。
- 精确关系表：

| 概念 | 本质 | 谁决定检索 |
|---|---|---|
| 普通 RAG | 固定管线（问→查一次→答） | 代码/工程师写死 |
| Agentic RAG | 检索变成 Agent 工具，模型主动调用 | 模型自己（时机/次数/改写） |
| "Agent 的 RAG" | 口语，基本 = Agentic RAG | 同 Agentic RAG |

- **补充**：普通 RAG 不是"落后"，简单问答用普通 RAG 反而更省更快；只有需要"先查 A、发现缺口、补查 B、再改查 C"这种多步依赖检索时才值得上 Agentic RAG。

> **一句话**：RAG 被工具化就是 Agentic RAG；普通 RAG 是"检索写死在固定管线里、模型无决策权"，不是和 Agent 结合的硬编码问题。

## Q5. 【对应 HTML 问题 12】RRF 融合排序是重排（第 3 点）的一种方式吗？

**A：不是。** RRF 和 cross-encoder 重排是**先后两步、不同环节**：

| 步骤 | 环节 | 输入 | 做什么 | 方法 |
|---|---|---|---|---|
| 第 2 步内部 | 混合检索的**融合** | 向量榜 + BM25 榜 | 把两个排行榜合并成一个 | **RRF（只看排名位置，轻量）** |
| 第 3 步 | **重排** | 融合后 top-K 候选 | 逐对精细打分重新排序 | **cross-encoder（联合打分，重精度）** |

- **RRF 解决**"两套召回结果怎么揉成一列"——只按排名位置（第 1 名、第 2 名）合并，不看内容相关性深浅。
- **cross-encoder 重排解决**"揉好后谁真正最相关"——把 query + 每个文档拼一起送模型联合打分。
- 对应伪代码是两段独立逻辑：`hybrid(vector_search(q) + bm25(q))`（内部藏 RRF）→ `reranker.rerank(q, hits)[:5]`（才是重排）。
- **比喻**：RRF = 海选时把两位评委的名单合并成总入围榜；cross-encoder = 对入围者逐个细看打分的终极精评。

> **一句话**：RRF 是混合检索内部的榜单融合算法，重排是独立的 cross-encoder 精排步骤，不是一回事。

## Q6. 【对应 HTML 问题 12】cross-encoder 其实就是另一个模型去重排？一般是更强的模型？

**A：** 对，但要说清楚"强在哪"：
- 和召回模型不是同一个：**召回用 bi-encoder（双塔）**，query 和文档分开编码算相似度（快，能海量搜）；**重排用 cross-encoder**，把 query + 文档拼一起送进模型**联合打分**（准，但慢，只能对少量候选跑）。
- **"更强"强在架构**：bi-encoder 编码时 query 和文档零交互，只能靠最后向量距离；cross-encoder 让两者在模型内部逐 token 交叉注意力，能抓"这个词在 query 和文档里是不是一个意思"这类精细匹配。不是参数一定更大。典型：BGE-Reranker、Cohere Rerank、MonoBERT。
- **为什么不能全程用 cross-encoder**：它要 query+doc 配对算，没法预先建索引，不能做大规模召回。所以工程上是两阶段：**bi-encoder 快速海选 top-100 → cross-encoder 精排取 top-5**（先海选再终选）。

> **一句话**：cross-encoder 确实是另一个专门模型做重排，强在相关性判断精度（架构决定的联合打分），但只能精排 top-K，不能替代召回。

## Q7. 【对应 HTML 问题 12】切分只有按标点一种吗？父子块一定要用吗？

**A：两个都是"文档为背而简"造成的误会。**
- **切分方案按文本类型选，没有唯一正确**：

| 切法 | 适合场景 |
|---|---|
| 固定长度切（带 overlap） | 通用兜底 |
| 按标点/段落切 | 中文自然语言默认最优（语义完整） |
| 按结构切（Markdown 标题 / HTML / 函数） | 网页、文档库、代码库 |
| 语义切分 | 长文本、话题易变 |

- 块大小是**检索精度 vs 上下文完整度**的权衡：块小命准但上下文不足，块大上下文全但语义被稀释。`size=400, overlap=80` 只是示例值。
- **父子块不是必须**，是"命中要准 + 回答要全"冲突时的折中（小块检索、父块补上下文）。**主要适用于上下文依赖强的长文档**（论文、报告、书籍）；FAQ 这类自足碎片文档用单层块即可。对延迟/成本敏感也可简化。
- 生产建议：给每块注入元数据（来源、时间、章节）方便过滤。

> **一句话**：切分按文档类型选（标点切只是中文默认最优）；父子块是长文档上下文依赖场景的工具，不是必选项。三板斧都是场景工具，不是全上就对。

## Q8. 【对应 HTML 问题 12】修正版完整答案（替换用）

### 通俗版
想让 RAG 检索更准，核心是解决三个矛盾：**「切多大」**（块小语义碎、块大检索不精）、**「怎么找」**（只懂意思漏精确词、只认关键词漏同义表达）、**「谁排前」**（海选快不精、精评准太慢）。对应三大步：**选好切分 → 混合检索 → 二次重排**。

### 技术内核（面试怎么答）
**① 切分（Chunking）——按文档类型选：**
- 固定长度切（带 overlap，通用兜底）/ 按标点段落切（中文默认最优）/ 按结构切（标题、HTML、函数）/ 语义切分（长文本）。
- 核心权衡：**块大小 = 检索精度 vs 上下文完整度**，小到能精确命中、大到能自圆其说。
- **父子块不是必须**：是"命中准 + 回答全"冲突的折中，小块精确匹配 + 父块补上下文；主要适用上下文依赖强的长文档（论文/报告/书籍），FAQ 碎片文档用单层块。
- 给每块注入元数据（来源、时间、章节），便于过滤。

**② 混合检索（Hybrid Search）——两套互补再融合：**
- **稠密向量**（HNSW）：懂语义，处理同义改写；**稀疏 BM25**：懂精确词，处理专有名词、编号、生僻术语。两者互补缺一不可。
- 两套结果用 **RRF（倒数排名融合）** 合并——只按排名位置融合榜单，不看深度相关性，轻量高效。
- 反例：只靠向量查"Transformer"会搜出泛泛而谈；只靠 BM25 查"换电电池"搜不到"动力电池组"。

**③ 重排（Re-ranking）——粗排后精排：**
- 召回模型（bi-encoder）query 和文档分开编码，只能算相似度，**只能粗排**；
- **cross-encoder**（如 BGE-Reranker）把 query+文档拼一起联合打分，**对融合后的 top-K 精排**。
- 为什么分两段：cross-encoder 逐对打分、不能预先建索引，**没法对全量做**，只能"bi-encoder 海选 top-100 → cross-encoder 精排取 top-5"。

**评估分层**：检索层看 Recall@K / MRR；生成层看 Faithfulness / Answer Relevancy。**先量化再优化。**

### 避坑 / 拓展
- **别指望一招通用**：切分方案、是否父子块、要不要重排，按"文本类型 + 上下文依赖度 + 数据规模 + 延迟成本"分场景定。
- **优化顺序**：先调分块（收益最大）→ 加混合检索 → 最后上重排，每步用指标验证，别一把梭。
- 进阶：语义缓存（Redis + Sentence-BERT）拦截高频问法；领域自适应微调 Reranker 提升 Hit@3（数据量不够别微调）。

### 一句话记住
**切分按文档类型选、大小做权衡；向量懂意思 + BM25 懂精确词，RRF 合并；bi-encoder 海选、cross-encoder 精排。** 三板斧都是"场景工具"，不是"必须全上"。

## Q9. 【对应 HTML 问题 18】语义缓存缓存在哪？并发批处理为什么省 token？

**A：**

### 1. 语义缓存：缓存在哪、服务端还是客户端
- **缓存的是"问题 → 答案"的映射**。用户问过（或语义相近）的问题，直接返回存好的答案，不再调模型——省 token + 省延迟。
- **存在服务端（Redis）**，不是客户端。原文 `Redis + Sentence-BERT`，Redis 是服务端内存库，所有用户共享一份缓存（用户 A 问过、用户 B 问类似的也能命中，这才是它"拦掉 20–40% 请求"的原因）。
- **语义缓存 vs 普通缓存**：普通缓存按字符串 key（"北京天气"≠"北京今天天气怎么样"）；语义缓存先用 Sentence-BERT 把问题转向量，靠**语义相似度**命中——"北京天气"和"北京今天天气怎么样"向量相近就视为同一问题，复用率高得多。伪代码 `@cache(ttl=3600)` 是简化，真实语义缓存是：问题→embed→向量查 Redis→相似度超阈值就返旧答案（带过期时间）。

### 2. 并发批处理为什么省 token
- **省 token 的是"批处理"，不是"并发"**：并发主要省延迟/提吞吐；批处理才省 token。
- **机制**：大模型计费按 token，每次调用的固定开销（system prompt、指令前缀）每个请求都要付一遍。批处理把多个相似小请求拼成一次调用，固定开销只摊一次：
  - 不批处理：100 个问题各一次独立调用，system prompt 重复 100 遍。
  - 批处理：100 个问题拼一次，system prompt 只付 1 遍，固定开销从 20000 token 降到 200（省近 99%）。
- 前提：这些问题能共享同一段上下文/指令（同一类客服问答、同一知识库约束）。若彼此无关、各需不同长上下文，就没法这么拼。

| 手段 | 主要省什么 |
|---|---|
| 语义缓存 | 省 token + 省延迟（重复问题直接返答案） |
| 批处理 | 省 token（摊薄固定前缀/上下文） |
| 并发 | 省延迟/提吞吐（不省 token 总量） |
| 长上下文压缩 | 省 token（缩短每次送入的上下文） |

## Q10. 【对应 HTML 问题 19】元认知指令让 Agent 每步自问"是不是真的需要"，这个指令是放在 prompt 中吗？

**A：是的，就是放在 system prompt（指令）里的一段"自我约束"的话。** 它不属于代码逻辑，而是文字约束。所谓"元认知"= 让模型退一步审视"我这一步操作合不合理、是不是在绕圈"。例如："在执行下一步工具调用前，先确认这步是否真推进了任务；如果和上一步一样或结果已够，就直接给出最终答案。"

### 和"硬护栏"的区别（易混）
| 类型 | 是什么 | 在哪实现 |
|---|---|---|
| **软护栏**（元认知指令） | 每步自问"这步必要吗"，减少无效循环 | **prompt 层**（写进 system prompt） |
| **硬护栏** | 步数封顶、token 预算、连续 3 次相同 action 强制停、超时熔断 | **代码层**（伪代码 `for i in range(max_steps)`、`if (out.tool,out.args) in seen[-2:]`、`except TimeoutError`） |

- 软护栏是"软"的——模型不一定每次听话，所以才需要硬护栏兜底（伪代码 `return "已触发步数/重复护栏"`）。
- 而且软护栏不解决根因：循环往往因任务描述模糊或工具返回不可解析。原文强调要在 prompt 和工具 schema 上修根因，元认知 + 硬护栏只是"防炸"。

## Q11. 【对应 HTML 问题 23】企业实际项目开发中框架 LangGraph 用的多对吧？

**A：在"需要强可控、长流程、状态可恢复"的生产系统里，LangGraph 确实最主流——这点对。但要加场景限定，不能笼统说"所有企业最多"。**

- 原文定位：LangGraph = 可拖拽状态机，最可控、生产级（造"流水线工厂"）；选型"要可控 → LangGraph"。
- **分场景**（原文 + 之前 Q5 选型）：
  | 场景 | 主流选择 |
  |---|---|
  | 大型/复杂业务（状态机、长流程、强可控、可恢复） | **LangGraph（最主流）** |
  | 中小型/快速出产品 | OpenAI Agents SDK（轻量）、Dify/Coze 低代码、CrewAI |
  | 大厂多自研 | 字节 Coze、阿里百炼、百度千帆、腾讯元器等 |
- **更精确说法**：开源框架里 LangGraph 用得多；简单任务/快速原型企业反而用轻量 SDK 甚至直接调 API（Q22 避坑也提"别为用图而用图"，Anthropic 建议先 LLM API 写几行再上框架）；且大厂很多自研编排，不能说"所有企业 LangGraph 最多"。
- **面试加分**：把一个框架用透、讲清原理 + 踩坑，比泛泛罗列四个强（面试官常深挖你真用过的那一个）。

## Q12. 【对应 HTML 问题 24】上下文窗口爆炸：滑动窗口是什么？检索式记忆怎么展开？

**A：**

### 1. 滑动窗口
- = 维护一个固定大小的"最近 N 轮对话"队列，模型每次只看到窗口内内容，**窗口外的旧消息直接丢弃（不进上下文）**。
- 形象：只能显示最近 10 条的窗口，发第 11 条时窗口滑动——最顶上的第 1 条被推出丢掉，第 2~11 条成新窗口。永远只留最近 N 条。
- **关键点**：按"轮次/位置"无脑切，不挑内容；简单但可能误丢重要旧信息。所以常和"摘要压缩"组合：窗口留近期原文 + 更早的做成摘要（保留语义）。

### 2. 检索式记忆（只取相关片段进上下文）
- 历史/知识先全部**存到外部（向量库），不塞进上下文**；每次生成时，按**当前问题**语义检索"最相关几条片段"放进上下文，其余几十万字模型根本看不到，自然不爆仓。
- 流程：`历史/知识 → 切分+embed → 存向量库` → `新问题 embed` → `向量库召回 top-K` → `只把 top-K + 当前问题拼进上下文`。
- **它和 RAG 本质是一回事**：把记忆当 RAG 知识库，按需语义召回，不是全量装（呼应 Q4）。
- 与滑动窗口对比：

| | 滑动窗口 | 检索式记忆 |
|---|---|---|
| 挑什么留 | 最近 N 轮（按位置） | 和当前问题相关的片段（按语义） |
| 旧的存哪 | 直接丢 | 存外部向量库，可再召回 |
| 优点 | 极简单 | 不丢重要但久远的信息 |
| 缺点 | 可能误丢关键信息 | 需建库/embed，稍重 |

### 3. 补充：Claude Code 的 read-only 子 Agent 取信息
- **不是常驻固定的一个 Agent**，而是"按需临时派发的 read-only 角色"：每次需取大量信息时 spawn 一个子 Agent（复用角色定义，每次独立实例），干完销毁。
- 子 Agent 自己读大量文件（原始内容待在它上下文里），**只回传提炼结论给主 Agent**，主上下文从来没装过那几万字原文——对应第 24 题"上下文隔离 + 工具结果只留结论"的落地版（呼应 Q2 多 Agent 隔离价值）。

### 第 24 题"瘦身全家桶"
1. 摘要压缩（旧→小模型提炼关键事实）2. 滑动窗口（直接砍掉最近 N 轮外）3. 检索式记忆（历史存外部按需召回）4. 上下文隔离（多 Agent 各管局部上下文）5. 工具结果只留结论（1 万字返回 → 只存"查到 3 条相关订单"）。

## Q13. 【对应 HTML 问题 25】降级/替换里的"备用数据源就切换"指什么？举例说明

**A：** "备用数据源就切换" = 给同一信息准备第二/第三个获取渠道，**主源挂了/超时/不准就自动换另一个还能用的**——别把鸡蛋放一个篮子里。

### 例子
- **查天气**：主=和风天气 API，备=OpenWeatherMap。主 API 超时 500 → 自动切备用，用户无感知。
- **RAG 检索**：主=自建 Milvus 向量库，备=另一向量库实例 / 兜底 BM25 关键词索引。主库连不上 → 切备用或退化成关键词匹配先顶着（"降级"= 从精准模式降到能用模式）。
- **查订单**：主=MySQL 主库，备=从库 / Redis 旧数据。主挂 → 切从库（数据可能延迟几秒但能用）。
- **LLM 本身**：主=GPT-4o，备=GPT-4o-mini / 本地 7B。主限流 → 切便宜/本地模型兜底，质量降一点但服务不中断。

### 与"重试""改参数"的区别（原文三招分清）
| 手段 | 适用 | 例子 |
|---|---|---|
| 重试 + 退避 | 同一源临时抽风（超时、5xx） | API 偶尔 500，等几秒再试 |
| 改参数重调 | 不是源的问题，是你参数错了（4xx） | 日期格式错被拒 → 改格式再调（重试没用） |
| 切换备用源（降级） | 这个源彻底不可用/长期挂 | 主 API 挂 → 换服务商/从库/缓存 |
| 兜底回复 | 上面都救不了 | "暂时查不到，稍后再试" |

**关键**：重试是"同一个源再试"，切换是"换一个源"；一个源一直挂，重试 100 次也没用，必须切。工程上切换要自动 fallback + 监控告警（主源挂了有人去修，否则一直跑降级质量差还没人发现）。

## Q14. 【对应 HTML 问题 26】evaluator-optimizer 工作流：一个生成、一个评估，指的是不同的 Agent 吗？

**A：通常是不同的 Agent（或至少不同角色/不同次调用），原文明确推荐用"独立 critic Agent"。**

- 标准做法两个角色：**Generator**（产出）+ **Evaluator/Critic**（对照 rubric 挑毛病给反馈）。伪代码：`draft = generate(prompt)` → `review = critic.evaluate(draft, rubric)` → `draft = revise(draft, review.feedback)`。`generate` 和 `critic.evaluate` 是**两个独立调用**，理想是**两个独立 Agent 实例**。
- 实现形态三种：
  | 形态 | 是否不同 Agent |
  |---|---|
  | 独立 critic Agent（原文推荐） | ✅ 两个独立 Agent |
  | 同一 Agent 自我反思（self-Reflection） | ❌ 同一 Agent 分两次调用 |
  | 不同 prompt 同一模型 | ⚠️ 逻辑上不同 Agent |
- **为什么推荐独立 critic**：同一 Agent 自我反思容易"自己护自己"、挑刺不狠，变橡皮图章式敷衍通过（呼应 Q1 隔离价值）。独立 critic + 不看作者的私密推理，才能客观独立挑刺。
- 闭环多轮"生成→评→改"（伪代码 `for _ in range(2)`，一般 2~3 轮，再多 token 翻倍收益递减）。**注意 token 倍增**（生成+评估+修订至少 2~3 倍），只在质量敏感场景（写代码、写长文）用，别给每次闲聊加反思。

## Q15. 【对应 HTML 问题 28】无状态化+水平扩展、令牌桶限流、批处理、租户隔离

**A：**

### 1. 无状态化 + 水平扩展
- **无状态化**：每个请求自带完整信息（或从外部 Redis/DB 取状态），实例本身不存"用户聊到哪了"。对应 Q2 的滑动窗口/摘要——处理完的历史/摘要**外置到 Redis**，请求来了按需取，模型算完实例就丢（不长期持有跨请求历史）。
- **水平扩展** = 部署**多个相同服务副本**（实例 1/2/3…），前面负载均衡（Nginx）分发，忙了加副本、闲了缩。你之前问的"增加 CUDA 实例"是**推理层**扩（多 GPU/多 vLLM），Web 服务实例是**应用层**扩，两层都靠无状态才能玩。
- **关键**：无状态是"能随便加实例"的前提。若有状态（历史在实例内存），请求必须回老实例，就没法横向加机器。

### 2. 请求队列 + 令牌桶限流（保护后端不被打爆）
- **令牌桶**：桶每秒放固定数量令牌（如 1 万/秒），每个请求先抢一个令牌才能继续；抢不到（桶空=请求太多）就超阈值。伪代码 `if not bucket.consume(1): return "rate limited", 429`（429 = 被限流）。
- **超阈值两种处理**（原文"排队或快速失败"）：
  | 策略 | 做法 | 适用 |
  |---|---|---|
  | 快速失败 | 直接拒，返回 429 让客户端稍后重试 | 保护后端优先 |
  | 排队 | 进队列等，令牌恢复再处理 | 不想丢请求且后端能消化 |
- 为什么需要：10 万 QPS 涌来，后端（尤其 GPU）只能处理 1 万/秒，不限制会显存爆、雪崩。令牌桶=门口发号，满员拒客或排队，别压垮后厨。
- 配合降级：抢到令牌但 `overloaded()` 真过载 → 走降级（简化流程/转人工），不跑完整重链路。

### 3. 大模型也能和视觉模型一样批处理吗？
- **能**，vLLM 的 **continuous batching** 正是干这个：把多个并发请求凑一批一起算（GPU 并行算多序列），避免单请求独占 GPU 干等。LLM 自回归逐 token 生成，单请求 GPU 利用率低，batch 把多个请求填进空闲算力，利用率和吞吐直接上去。和视觉模型 batch 同一思路，只是 LLM 用 continuous batching（动态凑批）更灵活。

### 4. 租户隔离和高并发优化的关系
- **租户** = 不同客户/业务线/团队。不隔离时，租户 A 发疯式调 API 占满 GPU/连接池，**B/C/D 全被拖垮**——一家挤垮全场。
- **做法**：每个租户**单独配令牌桶**（A 超限只拒 A，不影响别人）+ 资源配额（每租户最多用 20% GPU）+ 必要时物理隔离（大客户单独部署）。
- 它放在"高并发设计"里是**稳定性/公平性**保障：高并发下保证"任何单一来源失控都不拖垮全局"，和限流/降级并列防雪崩。

## Q16. 【对应 HTML 问题 30】PII 是什么？能否给一版通俗易懂的回答？

**A：**

### PII 是什么
**PII = Personally Identifiable Information（个人身份信息）** = 能识别到"具体某个人"的信息：身份证号、手机号、银行卡号、邮箱、工资、病历、家庭住址、姓名+工号等。一旦进模型/出公网就有泄露个人风险，受 GDPR、国内个人信息保护法等监管，必须特殊保护。原文"敏感信息分级脱敏：工资、身份证这类 PII 先遮掉再进模型" = 把"13800138000""身份证 110xxx"**替换成 `[手机号]` `[身份证]` 再喂模型**，模型看不到真值自然泄露不了。

### 通俗版（重写，不晦涩）
**这题问什么**：Agent 要接企业真实数据（员工信息、客户资料、内部文档）才能干活，但数据敏感——泄露或乱改要出大事（违法、赔钱、丢客户）。问的是：怎么让 Agent 能干活又不搞出事。

**五个大白话原则：**
1. **敏感信息先打码再进模型**：像寄快递遮身份证号。工资、手机号、身份证先脱敏（换成`[已遮蔽]`），模型看不到真值，泄露不了。
2. **能私有化就私有化**：用自己机房部署的模型（本地/内网），别用公网 API。数据不出公司大门，外部厂商拿不到。最彻底降低泄露面。
3. **谁动了什么留账本（审计日志）**：Agent 每次调工具（查了谁、改了啥）记一条：谁、几点、干啥。出问题能追溯——"张三的 Agent 下午 3 点删了这条数据"。
4. **写操作必须人点头**：读数据风险小，删库/发邮件/转账这种写操作危险，必须设闸——Agent 想删东西先拿显式授权（人确认/权限网关），不能自己拍板。
5. **防被骗 + 留人工兜底**：外部内容（邮件、网页）可能藏指令骗 Agent 干坏事（提示注入），加护栏过滤；高风险动作保留人工兜底（人能随时叫停），任何输出能溯源到依据了哪条数据。

**一句话记住（通俗）**：企业用 Agent 安全底线 = 敏感信息先打码 + 尽量私有化不出门 + 每次操作留账本 + 改数据必须人授权 + 防被骗 + 出问题能追溯。

**面试加分（原文避坑）**：别以为"接了 MCP 就安全"——MCP 只是通信协议不替你做安全，暴露数据库还是得自己配连接串/权限/审计；安全要常态化测（定期红蓝对抗模拟攻击），别上线才想起来。

### 原文术语 → 白话对照
| 原文术语 | 白话 |
|---|---|
| PII 检测/脱敏 | 身份证、手机号先打码再喂模型 |
| 私有化/隔离部署 | 模型和数据在自己机房，不出公网 |
| RBAC + 审计日志 | 按角色给权限 + 每次操作留账本 |
| 安全沙箱 | 给 Agent 隔离间，干坏事也伤不到真系统 |
| Guardrails 输出过滤 | 给输出加护栏，过滤有害内容 |
| 提示注入防护 | 防外部内容骗 Agent 干坏事 |
| 全链路溯源 | 任何结果能追到依据了哪条数据 |
