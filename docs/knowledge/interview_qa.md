# YOLOE 商品主体检测项目

> 本文档基于项目代码实现、终版 resu 描述与目标 position（Agent 开发 / 大模型应用开发）整理。
> 回答策略：先讲做了什么（事实），再讲为什么这么做（思考），最后自然引出能力迁移（不硬蹭）。

## 一、Prompt Engineering 类

### Q1：你的分层 Prompt 体系具体是怎么设计的？为什么要分层？

**回答要点**：

- 顶层是通用词（toy / object / product / item）兜底召回；
- 中层是品类词（toy car、plush toy、building block 等大类）做主召回；
- 底层是细分类词（die-cast car、RC plane、fashion figure 等长尾）做召回补充；
- 共迭代 V0 → V10 共 10 个版本，每版基于上一版的漏检 case 增补，并删除通用词（如 V5 加 object/product/item 后效果下降，后续版本删除）。

**话术**：

> 我把 Prompt 拆成三层结构。顶层用通用词保证基础召回，中层覆盖主品类，底层补长尾。每一版迭代都是基于上一版的漏检样本做针对性扩展。比如 V5 我加了一批通用词想兜底，但发现通用词会稀释类别的语义信号，反而拖累 precision，后续就回退掉了。这套"通用兜底 + 品类主召回 + 长尾补充"的分层思路，本质上和 LLM Prompt 中的任务描述 + 约束 + 边界控制是一回事。

### Q2：你说做了对比实验，能具体讲一下实验设计吗？  回答不够好

**回答要点**：

- 单变量控制：固定测试集，每次只切换一个变量（模型 / 参数 / Prompt 列表）；
- 三类对比维度：①模型对比（不同 YOLOE 版本 / 不同 backbone 的精度和速度）；②参数调优对比（置信度阈值、最小面积比、最小边长、父子框阈值等）；③Prompt 对比（不同类别描述方式对召回率的影响）；
- 负面过滤：通过面积过小（<1‰）、边长过短（<10像素）、置信度过低（<0.1）三阈值过滤无效框；
- 评估指标：召回率（漏检数）、precision（误检数）、综合排序稳定性。

**话术**：

> 我用单变量对比实验，固定测试集，每次只切换一个变量。对比分三个维度：模型对比看精度和速度的平衡，参数调优对比看阈值对 precision/recall 的影响，Prompt 对比看不同类别描述方式对召回率的影响。比如同样是车类，"toy car" 召回广但会带进背景玩具，"die-cast car" 精准但漏掉遥控车，"RC car" 介于两者之间，最后用组合词。负面过滤这块，我用面积过小、边长过短、置信度过低三个阈值过滤无效框，避免引入需要人工维护的黑名单。整个流程是"假设 → 实验 → 验证 → 落地"，跟大模型 Prompt 调优的 A/B 测试方法论一致。

### Q3：Prompt 过多会有什么问题？你怎么决定上限？

**回答要点**：

- 主要问题是推理耗时：YOLOE 基于 CLIP 文本编码器，Prompt 列表越长，文本特征计算越慢，影响在线服务响应；
- 上限由两个约束共同决定：①推理耗时的 SLA 上限；②新增类别对召回率的边际收益；
- 决策方法：每加一个新类别，看漏检减少数（边际收益）和推理耗时增加（边际成本），收益小于成本就停止扩展；
- 实际收敛在 12–15 个核心类别 + 少量长尾补充。

**话术**：

> 过多 Prompt 主要问题是推理耗时。YOLOE 文本编码会随 Prompt 列表长度增长，对在线服务的响应时间有直接影响。上限不是拍脑袋定的，是两个约束共同决定的：一是推理耗时的 SLA 上限，二是新增类别对召回率的边际收益。我的做法是每加一个新类别，看漏检减少数和耗时增加的对比，当边际收益小于边际成本就停止扩展。最后收敛在 12-15 个核心类别 + 少量长尾补充。这套"边际收益 vs 边际成本"的决策思路，跟大模型场景里加 few-shot 示例数量的权衡是一致的。

## 二、算法设计类

### Q4：父子框判定为什么用强 + 弱双层判定？单层不行吗？

**回答要点**：

- 单层（只用强条件覆盖率 > 0.75）会漏掉"部分嵌套"配件——配件部分露出主体外，覆盖率在 0.4-0.75 之间，强条件命中不了；
- 弱条件兜底这部分场景：0.4 < 覆盖率 ≤ 0.75 且 面积比 < 0.3；
- 弱条件加"面积比 < 0.3"约束：区分"部分嵌套的小子框配件"和"部分嵌套的并列主体"（并列主体子框通常不小）；
- 两层命中区间不重叠（c > 0.75 vs 0.4 < c ≤ 0.75），互为补充。

**话术**：

> 单层判定会漏掉部分嵌套的配件。真实场景里有些配件只有一部分在主体框内，比如玩具的部分露出包装外，覆盖率在 0.4-0.75 之间，强条件命中不了。所以我加了弱条件兜底：覆盖率在 0.4-0.75 之间、且子框面积明显小于父框（面积比 < 0.3），判定为疑似配件。这里加面积比约束是为了把"部分嵌套的小子框配件"和"部分嵌套的并列主体"区分开——并列主体的子框通常不会远小于父框。两层命中区间不重叠，强条件解决完全嵌套，弱条件兜底部分嵌套。
>
> 至于为什么主判定用覆盖率而不是 IOU——评估过 IOU，但子框完全嵌套且远小于父框时，IOU ≈ 子框面积/父框面积，值会非常低，不如覆盖率（交集/子框面积）敏感。IOU 更适合两框大小相近的场景，父子框场景下覆盖率更合适。

### Q5：为什么强条件用 precision 衡量，弱条件用 recall 衡量？

**回答要点**：

- 强条件（覆盖率 > 0.75）：子框至少 75% 区域在父框内才达标，几何上几乎就是完全嵌套，命中的几乎都是确定配件框 → precision 高；
- 弱条件（0.4 < 覆盖率 ≤ 0.75 且 面积比 < 0.3）：命中的场景是"部分嵌套的小子框"，比强条件宽松，能补回强条件漏掉的疑似配件 → recall 高；
- 配合差异化惩罚：强条件命中直接置零权重（确定配件），弱条件命中轻度降权（疑似配件）。

**话术**：

> 强弱条件对应 precision/recall 是从几何特征推出来的。强条件覆盖率 > 0.75 要求子框至少 75% 在父框内，几何上几乎就是完全嵌套，命中的几乎都是确定配件，误判率低，所以对应 precision。弱条件覆盖率在 0.4-0.75 之间、面积比 < 0.3，命中的是"部分嵌套的小子框"，能补回强条件漏掉的疑似配件，但会带入少量不确定场景，所以对应 recall。配合差异化惩罚：强条件命中直接置零权重，弱条件命中权重乘 0.3 轻度降权。这样 precision 由强条件保住，recall 由弱条件兜底，两个指标分开优化而不是互相挤兑。

### Q6：多维综合打分为什么选置信度、面积、中心度这三个维度？

**回答要点**：

- 置信度：模型对检测框的置信，反映"是不是目标"；
- 面积：商品主体通常占画面较大比例，过滤背景小目标；
- 中心度：商品主图主体通常居中，过滤边缘裁切框；
- 三个维度覆盖了"是不是目标 / 是不是主体 / 是不是主图主体"三个层次。

**话术**：

> 单看置信度只解决了"是不是目标"，但商品场景里多个目标同时出现时，置信度高的不一定是主体。我加了面积维度解决"主体通常更大"，再加中心度解决"商品主图主体通常居中"。三个维度从"是目标 → 是主体 → 是主图主体"层层递进，组合起来才能稳定排到正确的主图主体。

### Q7：为什么用 min-max 归一化？另外两种方案什么时候用？

**回答要点**：

- min-max：把所有维度映射到 \[0, 1]，量纲统一，对业务最直观，是默认方案；
- Z-score：处理有离群值的场景，但负值不利于后续加权解释；
- Rank：对极端 outlier 最稳定，但丢失原始数值的相对差距信息；
- 通过归一化方案参数可切换，实测 min-max 在玩具类目效果最稳定。

**三种归一化方案对比表**：

> 说明：interview 时建议中英混用，首次出现说"中文名（英文）"，后续直接说英文。
> 话术示范："三种方案我都实现了：标准差归一化（Z-score）、最小最大归一化（min-max）、排名归一化（Rank）"。

| 维度          | Z-score（标准差归一化）                                                              | min-max（最小最大归一化）                                                   | Rank（排名归一化）                                                   |
| ----------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------- |
| **核心原理**    | 用"偏离均值多少个标准差"来衡量值的相对位置，转换后符合标准正态分布                                           | 用"值在最小值与最大值之间的相对位置"线性压缩到固定区间，本质是线性映射                               | 用"值在所有数据中的大小排名"代替原始数值，完全忽略数值差距，只保留顺序关系                        |
| **计算公式**    | z = (x - mean) / std                                                         | norm = (x - min) / (max - min)                                     | 按值从大到小排序的位次（最大值 rank=1）                                       |
| **计算示例**    | 原始\[0.3, 0.5, 0.2, 0.9] → mean=0.475, std≈0.27 → \[-0.65, 0.09, -1.02, 1.57] | 原始\[0.3, 0.5, 0.2, 0.9] → min=0.2, max=0.9 → \[0.14, 0.43, 0, 1.0] | 原始\[0.3, 0.5, 0.2, 0.9] → 排序后 0.9>0.5>0.3>0.2 → \[3, 2, 4, 1] |
| **值域**      | 有正有负，均值=0，标准差=1                                                              | \[0, 1]，最小值=0，最大值=1                                                | 1 到 N（N 为框数量）                                                 |
| **对离群值敏感度** | 敏感（离群值会拉大 std，其他值被压扁）                                                        | 敏感（离群值会成为 max，其他值被压到接近 0）                                          | 鲁棒（无论离群值多大，rank 只反映位次）                                        |
| **信息保留**    | 保留相对偏离程度                                                                     | 保留相对位置和数值差距                                                        | 仅保留大小顺序，丢失数值差距                                                |
| **业务可解释性**  | 差（负值难以解释"为什么主体得分是负的"）                                                        | 好（0-1 直观，"得分 0.85"业务方听得懂）                                          | 一般（rank 语义弱，"rank=2"含义不直观）                                    |
| **优点**      | 能识别相对偏离，统计意义强                                                                | 业务直观，值域统一，加权后综合得分仍在 \[0,1]                                         | 对极端 outlier 最稳定，不会让离群值拉偏结果                                    |
| **缺点**      | 产生负值，业务解释困难                                                                  | 对离群值敏感，极端值会压缩正常值的区间                                                | 丢失数值差距信息，同分情况多（多个框 rank 相同）                                   |
| **适用场景**    | 数据分布接近正态、需要统计意义的场景                                                           | 数据分布相对均匀、要求业务可解释的场景（项目默认）                                          | 数据有极端离群值、只关心排序不关心数值差距的场景                                      |
| **项目中的定位**  | 备选方案，适合离群点明显的图                                                               | 默认方案，玩具类目实测最稳定                                                     | 备选方案，适合极端 outlier 场景                                          |
| **备注**      | 防止 std=0 加了 eps 保护                                                           | 防止 max-min=0 加了 eps 保护                                             | 防止数据完全相同，单独处理 len(subjects)<=1 的情况                            |

**话术**：

> 三种方案我都实现了，通过配置切换。min-max 默认用，因为它把所有维度映射到 \[0,1]，加权后的综合得分语义清晰，便于解释。Z-score 适合数据有离群点的场景，但产生负值不利于业务解释。Rank 对 outlier 最鲁棒，但丢失了原始数值的差距信息。实测玩具类目 min-max 最稳定，所以默认走 min-max，其他类目按需切换。这套"多方案 + 可配置"的工程化思路，对应大模型应用里不同场景下的 Prompt / 参数切换策略。

## 三、工程化与服务化类

### Q8：检测结果的结构化输出怎么设计的？为什么要这么设计？

**回答要点**：

- 用 Pydantic 定义"主体信息"结构，包含：边界框、置信度、缩略图(base64)、面积占比、类别标签、是否为子框、综合得分；
- 字段含义清晰、可序列化、前端可直接消费；
- "是否为子框"和"综合得分"字段把算法决策（哪个是配件、哪个是主体）显式输出，下游可直接用，不用重算；
- 诚实定位：这是常规的工程化设计，不算项目核心亮点。项目真正的亮点在 Prompt 调优方法论和父子框判定算法，结构化输出只是配套的工程实践。

**话术**：

> 这是常规的工程化设计，用 Pydantic 定义结构，字段含义清晰，前端可以直接消费。"是否为子框"和"综合得分"这两个字段把后处理决策也输出出来，下游不用重算。我不把这个当成项目亮点，这就是基础工程实践。项目真正的亮点在 Prompt 调优方法论和父子框判定算法，结构化输出只是配套让这些算法结果能被下游使用。

### Q9：批处理是怎么设计的？性能怎么保证？

**回答要点**：

- 分块并行：分块大小可配（默认 16，最大 64）；
- CPU 预处理 + GPU 推理分离：CPU 线程数和 CUDA Stream 数量都可配；
- 动态批处理：批大小上限 + 最大等待时间控制批的合并策略；
- 并发下载：异步信号量限流到 20 并发，平衡带宽和内存。

**话术**：

> 批处理分三层并行：CPU 预处理、GPU 推理、网络下载。CPU 端用多线程预处理，GPU 端用 CUDA Stream 提高吞吐，网络端用异步信号量限流到 20 并发防止打爆内存。批大小和等待时间通过参数可配，业务方能按图片大小和 SLA 自己调。整套设计的核心是把"CPU 密集 / GPU 密集 / IO 密集"三类任务解耦，避免互相阻塞。

### Q10：可配置的参数体系具体包含哪些？

**回答要点**：

- 检测参数：置信度阈值、最小面积比、最小边长、最大主体数；
- 排序参数：三维度权重（置信度 0.4 / 面积 0.5 / 中心度 0.1）；
- 父子框参数：覆盖率阈值、IOU 阈值、面积比阈值、惩罚系数；
- 归一化方案选择：Z-score / min-max / Rank 三选一；
- 批处理参数：分块大小、并发数、批大小、超时时间。

**话术**：

> 整套参数分四类：检测、排序、父子框、批处理。每类都有默认值，但都暴露成可配置项。业务方可以通过 API 动态调整，不需要重启服务。这套设计的出发点是"不同业务场景对 precision/recall 的偏好不同"，比如玩具类目可以放宽阈值保召回，logo 类目需要收紧阈值保 precision，靠参数而不是改代码适配。

## 四、与目标 position 的能力迁移类

### Q11：YOLOE 的 Prompt 调优和 LLM 的 Prompt Engineering 有什么相通点？

**回答要点**：

- 方法论层面（核心相通点）：
  - 迭代思路：都基于上一版失败 case 增补优化，YOLOE 是 V0→V10 基于漏检 case 迭代，LLM 是基于 bad case 迭代 system prompt；
  - 对比实验：都采用单变量控制 + 量化指标验证，不凭感觉调；
- 技术层面（部分相通）：
  - 分层设计：YOLOE 三层 Prompt（通用词 + 品类词 + 长尾词）和 LLM 三层 prompt（system message 里的角色定位 + 任务约束 / few-shot 示例）的分层思路相通；
  - 负面过滤：YOLOE 黑名单后处理过滤和 LLM negative prompt 思路相通（虽然实现机制不同）；
- 不相通的部分（诚实承认）：
  - YOLOE 没有真正的"任务描述"（不像 LLM 有 system prompt 定位角色），任务边界是通过类别列表整体设计隐式表达的；
  - 类别约束机制不同（YOLOE 列表 vs LLM system prompt），不能强行说相通。

**话术**：

> 真正相通的是方法论。第一，迭代思路一样——YOLOE 我是基于每版漏检 case 迭代到 V10，LLM 调 system prompt 也是基于 bad case 迭代，都是数据驱动不是凭感觉。第二，对比实验方法论一样——都是单变量控制加量化指标验证。第三，分层设计思路相通——YOLOE 三层 Prompt 和 LLM 三层 prompt 的分层逻辑是一致的。第四，负面过滤思路相通——YOLOE 黑名单后处理和 LLM negative prompt 都是告诉模型"不要什么"。
>
> 但也有不相通的地方，比如 YOLOE 没有真正的任务描述机制，任务边界是通过类别列表整体设计隐式表达的，这点和 LLM 的 system prompt 不完全一样。我不会强行说所有点都相通，但方法论层面的迭代、对比实验、分层设计、负面过滤这些是真正可迁移的。

**补充说明：LLM 三层 prompt 与 prompt 角色的区别**（被追问时展开讲）

**1. LLM API 标准的"prompt 角色"分类（按 message role 分）**

LLM 调用时 messages 列表有三种标准角色，这是业界通用分类：

| 角色类型 | 含义 | 典型内容 | 是否多轮 |
|---|---|---|---|
| **system** | 系统/角色定位 | "你是一个玩具分类助手，只能回答玩具分类问题" | 单条，通常放最前面 |
| **user** | 用户输入 | "这是一只毛茸茸的泰迪熊" | 多轮，可重复 |
| **assistant** | 模型回复 | `{"category": "毛绒玩具"}` | 多轮，可重复 |

调用示例：
```python
messages = [
    {"role": "system", "content": "你是一个玩具分类助手..."},
    {"role": "user", "content": "这是一只毛茸茸的泰迪熊"},
    {"role": "assistant", "content": '{"category": "毛绒玩具"}'},
    {"role": "user", "content": "能遥控的四驱车"},
    {"role": "assistant", "content": '{"category": "遥控车"}'},
    {"role": "user", "content": "拼装积木颗粒"}   # 真正的用户请求
]
```

**2. LLM Prompt 的"三层内容逻辑"分类（按内容职责分，非业界标准术语）**

这是从内容职责角度的分层，**不是业界标准术语**，interview 时不要用自造词（如"task prompt"这种），直接说"角色定位"和"任务约束"：

| 层级 | 内容职责 | 放在哪个 message 里 | 典型内容 | YOLOE 对应 |
|---|---|---|---|---|
| **第1层：角色定位** | 定义"是谁、做什么" | system message 的前半部分 | "你是一个玩具分类助手" | 通用词（toy, object） |
| **第2层：任务约束** | 定义"具体怎么做、输出什么" | system message 的后半部分 | "可选类别：[毛绒, 遥控车...]，输出 JSON" | 品类词（teddy bear, toy car） |
| **第3层：few-shot 示例** | 用具体示例引导输出 | user/assistant message 对 | 示例输入+输出 | 长尾词（die-cast car, RC car） |

**3. 两者的关系**

- "prompt 角色"（system/user/assistant）是 **API 层面**的标准分类；
- "三层内容逻辑"（角色定位/任务约束/few-shot）是 **内容职责层面**的分层；
- 第1层和第2层通常都放在 system message 里，第3层放在 user/assistant message 对里；
- 两个维度不冲突，但不要混着说——interview 时要说清楚是按哪个维度分的。

**4. YOLOE 与 LLM 分层思路的相通点**

| 维度 | YOLOE | LLM | 是否相通 |
|---|---|---|---|
| 分层粒度递进 | 通用词→品类词→长尾词（粗→中→细） | 角色定位→任务约束→few-shot（粗→中→细） | ✅ 思路相通 |
| 每层职责单一 | 第1层定义范围、第2层锁定主召回、第3层补充边缘 | 第1层定义身份、第2层定义规则、第3层给示例 | ✅ 思路相通 |
| 可独立迭代 | V0→V10 基于漏检 case 调某一层 | 基于失败 case 调某一层 | ✅ 思路相通 |
| 实现机制 | 类别词列表（模型前向约束） | 自然语言文本（message 输入） | ❌ 机制不同 |
| few-shot 机制 | 长尾词只是类别补充，不是示例样本 | few-shot 是真正的输入输出样本 | ❌ 机制不同 |

**5. interview 时被追问"三层 prompt 具体指什么"怎么回答**

> LLM API 标准的 prompt 分类是按 message 角色分——system、user、assistant。我说的"三层 prompt"是按内容职责分的：角色定位和任务约束通常都放在 system message 里，few-shot 示例放在 user/assistant message 对里。和 YOLOE 相通的是内容层面的分层思路——都是从粗粒度范围定义到具体约束再到边缘补充，但实现机制不同，YOLOE 是类别列表，LLM 是自然语言 message。

### Q12.1：你说的"实验方法论迁移到 Agent 调优"，能具体举例吗？

**回答要点**：
三个典型迁移场景：

- Function Call 工具选择调优；
- LLM system prompt 调优；
- RAG 检索参数调优。

**话术**：

> 三个典型场景：
>
> **场景1：Function Call 工具选择调优**。Agent 有多个可用工具（搜索、计算器、代码执行），需要决定什么场景调用什么工具。方法论迁移：固定测试集和 prompt，只切换工具选择策略（比如按意图分类 vs 让 LLM 自己决定），统计调用准确率和任务完成率，选指标最优的方案。
>
> **场景2：LLM system prompt 调优**。调 system prompt 让 LLM 在特定业务场景输出更稳定。方法论迁移：分层设计（顶层角色定位 + 中层任务约束 + 底层 few-shot 示例，对应 YOLOE 的通用词+品类词+长尾词），固定测试集切换 system prompt 版本，统计输出合格率，用 negative prompt 抑制幻觉输出（对应 YOLOE 黑名单过滤）。
>
> **场景3：RAG 检索参数调优**。RAG 系统召回的 chunk 质量影响最终回答。方法论迁移：固定 query 和 LLM，只切换 chunk\_size 或 top-k，统计召回 chunk 的相关性和最终回答准确率，选指标最优的参数组合。
>
> 这三个场景的核心思路都是一样——不凭感觉调，靠单变量控制 + 对比实验 + 量化指标驱动决策，跟 YOLOE Prompt 调优的方法论完全一致。

### Q13：你这个项目有什么不足？如果重做你会怎么改？  修改 回答不够好

**话术**：

> 主要两个不足。
>
> 第一，父子框判定完全基于几何特征，但有些场景几何特征区分不了。比如"部分嵌套且子框面积接近父框"的情况，几何上看既像配件又像并列主体，我现在的做法是判为并列主体，因为这种场景下面积比不达弱条件阈值。这是几何方法的固有边界，不是调参能解决的。如果重做，我会引入类别语义辅助——比如两个框的类别是"玩具车"和"遥控器"，即使几何上像父子，语义上也应判为并列主体。这就把判定从"纯几何"扩展到"几何+语义"。

### Q14：你说差异化惩罚是强条件置零、弱条件乘 0.3，这个 0.3 是怎么定的？

**回答要点**：

- 基于实验对比：在测试集上对比 0.1 / 0.3 / 0.5 三档，0.1 太激进（疑似配件基本被压没），0.5 太弱（疑似配件仍可能反超主体），0.3 是 precision/recall 平衡最优；
- 0.3 的语义：疑似配件框的综合得分被压到原来的 30%，足够排在主体框之后，但不会完全消失，便于后续业务层做二次判断。

**话术**：

> 0.3 是实验出来的。我对比了 0.1、0.3、0.5 三档。0.1 太激进，疑似配件基本被压没，等于丢了 recall；0.5 太弱，疑似配件可能反超真主体，丢了 precision；0.3 是两边平衡最优。而且 0.3 这个值的语义是"压到原来的 30%，排在主体之后但不消失"，下游业务层还可以做二次判断，留了余地。

## 六、技术选型类

### Q15：为什么选 YOLOE 不选 YOLOv8 / Grounding DINO？

**回答要点**：

- YOLOv8：闭集检测，预定义类别无法覆盖玩具这种长尾场景，业务上扩展困难；
- Grounding DINO：开放词表能力强但推理慢（单图秒级），不适合高并发服务化；
- YOLOE：开放词表（Open-Vocabulary）+ 实时推理（毫秒级），同时支持 prompt-based 和 prompt-free 两种模式，业务上能动态切换提示词而不需要重训模型。

**话术**：

> 选 YOLOE 是因为三个原因。第一，玩具是长尾类目，YOLOv8 这种闭集模型覆盖不了，加新类别要重训，业务接受不了。第二，Grounding DINO 开放词表能力强但单图推理到秒级，高并发场景扛不住。第三，YOLOE 同时支持 prompt-based 和 prompt-free 两种模式，业务上能按场景切换提示词策略而不用重训，工程灵活性最好。这套选型思路本质是"开放能力 + 实时性能 + 业务灵活性"三角权衡。

### Q16：YOLOE 的 prompt-based 和 prompt-free 两种模式你怎么选？

**回答要点**：

- prompt-based（提示词模式）：用文本提示词约束检测范围，适合类目明确的场景（玩具、logo）；
- prompt-free（无提示词模式）：不需要提示词，适合类目未知或全图主体定位的场景；
- 通过开关参数动态切换，业务方按场景选择，不用重启服务。

**话术**：

> 提示词模式适合类目明确的场景，比如玩具类目我用 12-15 个玩具 Prompt 列表约束检测范围，precision 高。无提示词模式适合类目未知或全图定位主体的场景，比如 logo 识别不依赖文本提示。两种模式通过开关参数动态切换，业务方按场景选择。

### Q18：多维打分中如果某个维度数据分布异常（如所有框置信度都很接近），min-max 归一化怎么处理？

**回答要点**：
- min-max 在 batch 内归一化，把最小值映射到 0、最大值映射到 1，即使原始差异很小，相对排序仍然清晰；
- 如果所有框置信度都很接近，min-max 会把微小的差异放大——最差的变 0、最好的变 1，保证该维度仍能区分排序；
- 如果某个维度所有值完全相同（无法区分），min-max 通过 eps 保护避免除零，该维度对所有框贡献相同，排序由其他维度差异决定；
- 置信度权重 0.4、面积权重 0.5、中心度权重 0.1——如果置信度区分不开，面积和中心度的差异会主导排序；
- 这是 min-max 在业务场景下的优势：保留相对位置，值域统一，综合得分始终在 [0, 1] 便于业务解释。

**话术**：
> min-max 在 batch 内归一化，把最小值映射到 0、最大值映射到 1。如果所有框置信度都很接近，min-max 会把这微小的差异放大——最差的变 0、最好的变 1，保证该维度仍能区分排序。如果某个维度所有值完全相同，min-max 通过 eps 保护避免除零，该维度对所有框贡献相同，排序就由其他维度的差异主导。比如置信度区分不开时，面积权重 0.5 和中心度权重 0.1 的差异会主导排序。这也是我选 min-max 的原因——保留相对位置，值域统一，综合得分始终在 [0, 1] 便于业务解释。

**话术**：

### Q20：Prompt 调优时怎么区分是 Prompt 问题还是模型本身能力问题？

**回答要点**：
- 判断依据：同一张图、同一模型，只切换 Prompt 列表，看检测框数量和类别变化；
- Prompt 问题的特征：换 Prompt 后召回有明显变化（如"toy car"换"RC car"漏检数明显减少）；
- 模型能力问题的特征：无论怎么换 Prompt，某类目标始终检测不到（如极小目标、重度模糊目标）；
- 实际处理：Prompt 问题通过迭代列表解决，模型能力问题靠阈值过滤或接受漏检；
- 方法论价值：这种"区分问题来源"的思路，和 LLM 调优里"区分是 Prompt 问题还是模型本身能力上限"一致。

**话术**：
> 判断依据是单变量对比。同一张图、同一模型，只切换 Prompt 列表，看检测框数量和类别变化。如果换 Prompt 后召回有明显变化，比如"toy car"换"RC car"漏检数明显减少，这是 Prompt 问题，通过迭代列表解决。如果无论怎么换 Prompt 某类目标始终检测不到，比如极小目标或重度模糊目标，这是模型能力上限，靠阈值过滤或接受漏检。这种"区分问题来源"的思路，和 LLM 调优里区分是 Prompt 问题还是模型本身能力上限是一致的——不是所有问题都能靠 Prompt 解决，得先定位问题在哪一层。

### Q21：你的检测置信度阈值为什么定 0.1 这么低？

**回答要点**：

- YOLOE 在开放词表场景下置信度分布偏低（玩具类目 prompt 不一定能完全匹配）；

- 这是"宽进严出"的设计：阈值低放进来，靠后处理筛选。

**话术**：

> 0.1 看起来低，但 YOLOE 开放词表场景下置信度本身就偏低，prompt 和图像不一定完全匹配。阈值定低是为了保 recall，避免漏检；precision 的问题靠后处理解决——多维打分会把低质量框排到后面，父子框判定会把配件框压下去。整体是"宽进严出"的设计，阈值低放进来，靠后处理筛选。

- 持续迭代：根据线上漏检/误检 case 反馈到下一版 Prompt 迭代。

**话术**：

> 两阶段验证。离线评估走对比实验，量化指标确定最优配置。线上验证抽样真实流量跑批，人工 spot check 排序结果。线上发现的漏检和误检 case 会反馈到下一版 Prompt 迭代。这套"离线评估 → 线上验证 → 持续迭代"的闭环，和大模型应用的上线流程一致。

## 九、与大模型结合的延展类

### Q24：如果要把这个检测服务接入大模型做商品理解 Agent，你会怎么设计？

**回答要点**：

- 检测服务作为 Tool：通过 OpenAI Function Call 或 MCP 协议暴露给 LLM；
- 结构化输出对齐：当前 Pydantic 输出已经可序列化为 JSON，LLM 可直接消费，不需要额外适配；
- 触发逻辑：LLM 侧决定什么时候调用检测 Tool（如用户问"这张图里有什么玩具"时触发）。

**话术**：

> 设计上分两步。第一，检测服务封装成 Tool，通过 Function Call 或 MCP 暴露给 LLM。第二，结构化输出对齐，当前 Pydantic 输出已经是 JSON 可序列化的，LLM 可以直接消费，不需要额外适配。触发逻辑在 LLM 侧决定——比如用户问"这张图里有什么玩具"时调用检测 Tool，拿到 bbox 和类别后由 LLM 生成回答。我项目里的结构化输出设计已经满足这一步的接口要求，不需要额外改造。

### Q25：你的结构化输出设计跟 LLM Function Call 的 schema 设计有什么关系？

**回答要点**：

- 都是"自描述 + 可序列化 + 可消费"的结构；
- YOLOE 输出的"主体信息"结构对应 Function Call 的返回值 schema（每个字段都有明确语义）；
- 区别：Function Call 还需要描述触发条件（什么时候调用），YOLOE 的检测是被动调用，触发逻辑在 LLM 侧。

**话术**：

> 本质上是同一类设计问题——怎么把工具的输出结构化，让上层能直接消费。我定义的"主体信息"结构相当于 Function Call 的返回值 schema，每个字段都有明确语义。区别在于 Function Call 还要定义触发条件（什么时候该调用这个 Tool），这部分逻辑在 LLM 侧，但 Tool 输出的设计思路是相通的。

## 十、工程化深挖类

### Q27：父子框判定中"面积比 < 0.3"这个阈值是怎么定的？

**回答要点**：

- 面积比用于区分"子框明显小于父框的配件"和"面积接近的并列主体"；
- 0.3 是基于业务场景观察的经验值——玩具场景下配件（如遥控器、小零件）面积通常不到主体的 30%；
- 如果阈值定太高（如 0.5），会把并列主体误判为配件；太低（如 0.1）会漏掉中等配件；
- 这个阈值作为可配置参数暴露，业务方可按场景调整。

**话术**：

> 面积比 0.3 是基于玩具场景观察的经验值。玩具场景下配件——比如遥控器、小零件——面积通常不到主体的 30%，所以 0.3 能比较好地区分"小子框配件"和"面积接近的并列主体"。如果阈值定太高比如 0.5，会把并列主体误判为配件；太低比如 0.1 又会漏掉中等配件。这个阈值作为可配置参数暴露，业务方可以按场景调整，比如 logo 类目可能需要不同的阈值。

# 项目亮点总结（回答时尽量往这些点靠）

## 亮点 1：完整的 Prompt Engineering 方法论（核心亮点）

**支撑材料**：

- V0→V10 共 10 个版本迭代，每版基于上一版漏检 case 增补；
- 三层 Prompt 体系（通用兜底 + 品类主召回 + 长尾补充）；
- 对比实验 + 单变量控制 + 量化指标验证；
- 负面过滤策略（黑名单 'person'）。

**核心话术**：

> 我建立了完整的 Prompt 迭代方法论：分层体系设计 → 对比实验验证 → 量化指标评估 → 持续迭代优化。这套方法论在 YOLOE 和 LLM 场景都适用。

## 亮点 2：precision/recall 权衡的工程化落地

**支撑材料**：

- 父子框双层判定：强条件（覆盖率>0.75）保 precision，弱条件（0.4<覆盖率≤0.75 且 面积比<0.3）兜底 recall；
- 评估过 IOU 但选覆盖率：子框完全嵌套且远小于父框时，IOU ≈ 子框面积/父框面积，值会非常低，不如覆盖率敏感；
- 差异化惩罚：强条件置零、弱条件×0.3（基于 0.1/0.3/0.5 三档对比实验确定）；
- "宽进严出"设计：阈值低放进来，靠后处理筛选。

**核心话术**：

> 我把机器学习里 precision/recall 权衡的思路落地到工程实现，通过强/弱条件 + 差异化惩罚，让两个指标分开优化而不是互相挤兑。

## 亮点 3：多方案可配置的工程化设计

**支撑材料**：

- 三种归一化方案（Z-score / min-max / Rank）通过参数切换；
- 四类参数体系（检测、排序、父子框、批处理）全部可配；
- prompt-based / prompt-free 双模式动态切换。

**核心话术**：

> 我没有把方案写死，而是把多个备选方案都实现并通过参数暴露，业务方按场景切换。这套"多方案 + 可配置"的工程化设计能适配不同业务场景而不改代码。

## 亮点 4：工具化封装 + Agent 可调用性（注意：非核心亮点）

**诚实定位**：

- 这只是常规工程实践，不是项目核心亮点；
- 结构化输出、RESTful API 封装是基础要求，不强行拔高；
- 项目真正的亮点在亮点1（Prompt 调优方法论）、亮点2（precision/recall 权衡工程化）、亮点3（多方案可配置）。

**支撑材料**：

- 视觉模型包装成 RESTful API，Agent 可直接调用作为视觉感知工具；
- 输出结构可序列化，下游可直接消费（但这是基础工程实践）。

**核心话术**：

> 工具化封装和结构化输出是基础工程实践，不算项目亮点。如果要说和 Agent 的关系，主要是这套 API 可以被 Agent 直接调用作为视觉感知工具，实验方法论也可以迁移到 Agent 调优，但这些是"可复用"而不是"创新点"。项目真正的亮点在 Prompt 调优方法论和父子框判定算法。

## 亮点 5：批处理三层并行的性能优化

**支撑材料**：

- CPU 预处理 + GPU 推理 + 网络下载三层并行；
- 异步信号量限流防打爆内存；
- 分块大小 / CUDA Stream / 预处理线程数全可配；
- 模型预热避免首次推理延迟。

**核心话术**：

> 批处理设计的核心是把 CPU 密集、GPU 密集、IO 密集三类任务解耦并行，避免互相阻塞。参数全可配，业务方按图片大小和 SLA 自己调。

## 亮点 6：实验驱动的参数调优（而非拍脑袋）

**支撑材料**：

- 惩罚系数 0.3 来自 0.1/0.3/0.5 三档对比实验；
- 阈值参数都基于实际测试集调优；
- 每版 Prompt 迭代都基于上一版漏检 case。

**核心话术**：

> 所有关键参数都不是拍脑袋定的，而是基于对比实验和量化指标确定的。比如惩罚系数 0.3 是在 0.1/0.3/0.5 三档对比中选出来的 precision/recall 平衡点。这套实验驱动的调优思路，跟大模型 Prompt 调优的 A/B 测试方法论一致。
