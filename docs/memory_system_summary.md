# Agent三层记忆系统总结  8.26

## 📚 三层记忆核心知识点

### 1. 工作记忆（Working Memory）

**定义**：即时上下文窗口，存储当前对话中的所有信息，相当于Agent的"短期记忆"

**特点**：
- 存储位置：内存
- 生命周期：当前会话
- 容量限制：受模型上下文窗口限制（如GPT-4的128K tokens）
- 主要作用：处理当前对话上下文

> 注：工作记忆的**容器**本身是模型侧的易失上下文（每次推理现取现用、用完即弃），LangChain 并不提供这个"容器"本身；但它提供了 `ConversationBuffer` / `Window` / `Summary` 等工具，专门管理"**当前会话**的对话历史如何暂存、裁剪、摘要，再喂进工作记忆"——这些是对工作/短期记忆的**管理实现**（属工作/短期记忆，而非情景记忆）。情景记忆（第 2 节）是**带时间戳、可持久化、可按时间检索**的事件记录库；其典型形态是跨会话沉淀，但"跨会话"是部署结果而非定义强制。
两点厘清：① 检索默认按 `thread_id` 限定在当前会话（当前会话消息在主流分类中称"对话历史/短期记忆"，本文档为简洁并入工作记忆）；跨会话需独立机制（LangGraph `Store` / PostgreSQL+pgvector 历史库）按 user_id 检索，不接则无。② 仅把当前 thread 状态持久化（如 checkpointer）仍是 thread 隔离的短期记忆，**不算情景记忆**；只有把交互带时间戳地沉淀进那个可跨会话检索的独立库，才成为情景记忆。
**LangChain 三层记忆组件（工作/短期记忆管理，非情景记忆）**：
- `ConversationBufferMemory`：把**当前会话**所有对话历史原样暂存 → 工作/短期记忆的"完整缓冲"策略
- `ConversationBufferWindowMemory`：只保留当前会话最近 k 轮 → 工作/短期记忆的"滑动窗口"策略
- `ConversationSummaryMemory`：自动摘要当前会话较早的对话 → 工作/短期记忆的"压缩/摘要"策略
---

### 2. 情景记忆（Episodic Memory）

**定义**：过往交互的历史记录，存储用户与Agent的所有历史对话，相当于Agent的"中期记忆"

**特点**：
- 有时间戳：每条记录关联具体时间
- 描述事件："什么时候发生了什么"
- 检索方式：时间范围查询（60%）+ 向量搜索（5%）
- 主要应用：历史回溯、合规审计、数据分析

**实现方案**：
- 存储原文：PostgreSQL的JSON列
- 存储向量：同一张表的VECTOR列（pgvector扩展）
- 不需要额外建立关系：原文和向量在同一行，自动关联

**企业取舍策略**：
- 只存重要会话（减少80%存储量）
- 摘要代替原文（减少90%存储量）
- 定期清理（保留30天）
- 分层存储（热/温/冷）


- 说明：`MemorySaver`（LangGraph checkpointer）按 `thread_id` 持久化**完整会话 State**，属于"跨会话的会话级状态存储"，更接近情景记忆的"原样存储"载体（前提是其真正跨运行持久化，而非仅本进程内存）；生产换成 **Redis** 是把它从进程内存变外部存储（仍是会话级状态），换成 **Milvus** 这类向量库则通常服务于**语义记忆**检索——二者**不是同一层**，勿混用。
- 关键区分：这三类的本质是"把**当前会话**历史暂存/裁剪/摘要、再喂进工作记忆"的**工作/短期记忆管理机制**；情景记忆（见上）是**带时间戳、可持久化、可事后按时间检索**的事件记录库（如 PostgreSQL+pgvector、`ChatMessageHistory`+DB），典型形态为跨会话沉淀。当前会话的对话原文本就属于工作记忆，只有沉淀进那个持久库才成为情景记忆。

---

### 3. 语义记忆（Semantic Memory）

**定义**：用户相关的事实、知识库、规则和约束，相当于Agent的"长期记忆"

**特点**：
- 无时间戳：事实本身没有时间属性
- 描述事实："什么东西是什么"
- 检索方式：向量相似度搜索（90%）
- 主要应用：个性化推荐、智能客服、智能问答

**实现方案**：
- 存储方式：向量数据库（Milvus、Chroma、Pinecone）
- 检索方式：语义相似度搜索

**提取策略**：
- 规则实时提取（60%）：关键词匹配，如"我喜欢XX" → "用户偏好XX"
- 关键事件触发（5%）：投诉、退款等事件时调用LLM
- 批量提取（35%）：每天凌晨运行，批量处理昨天的对话

---

## 📊 三层记忆对比

| 维度 | 工作记忆 | 情景记忆 | 语义记忆 |
|------|---------|---------|---------|
| **时间属性** | 当前会话 | 有时间戳 | 无时间戳 |
| **内容类型** | 对话历史 | 事件、经历 | 事实、知识 |
| **描述方式** | 当前上下文 | "什么时候发生了什么" | "什么东西是什么" |
| **存储位置** | 模型侧易失内存（每次推理现取现用） | 持久化历史库（典型跨会话）：PostgreSQL+pgvector（ChatMessageHistory+DB）/ 外部检查点（Redis 等） | 向量数据库 |
| **检索方式** | 顺序读取 | 时间范围+向量 | 相似度检索 |
| **生命周期** | 当前会话 | 长期（有取舍） | 长期（可更新） |

## ❓ Q&A总结

### Q1: LangChain中如何实现三层记忆？

**A1**: 
- **工作记忆**：模型侧易失上下文，LangChain 不专门"实现"它；`ConversationBufferMemory` / `Window` / `Summary` 这三类是对"**当前会话**历史如何暂存、裁剪、摘要，再喂进工作记忆"的**工作/短期记忆管理**实现（见情景记忆章节上方的 LangChain 组件说明），不属于情景记忆。
- **情景记忆**：用 `ChatMessageHistory` + 数据库持久化（或 `MemorySaver` 跨运行存完整 State）沉淀成**带时间戳、可持久化、可事后检索**的历史库（PostgreSQL+pgvector），典型形态为跨会话。注意 `Buffer`/`Window`/`Summary` 管的是当前会话窗口，归工作记忆，不是情景记忆的策略。
- **语义记忆**：LangChain不原生支持，需要向量数据库（Chroma/FAISS）+ 自定义管理

---

### Q2: ChatMessageHistory在哪里使用？

**A2**: 主要用在两个地方：
1. **保存会话时**：用`messages_to_dict()`把ChatMessageHistory转成字典，存到数据库
2. **加载会话时**：用`messages_from_dict()`把数据库的字典转回Message对象

---

### Q3: 情景记忆如何存储？原文和向量分开存吗？

**A3**: 推荐用PostgreSQL + pgvector，一张表搞定：
- **原文**：存在PostgreSQL的JSON列
- **向量**：存在同一张表的VECTOR列
- **优势**：不需要建立关系，原文和向量在同一行，自动关联

---

### Q4: PostgreSQL + pgvector是什么？向量相似度需要自己实现吗？

**A4**: 
- PostgreSQL 是传统关系型**数据库**；pgvector 是给 PostgreSQL 加装的**向量扩展插件**（"向量扩展插件"指的是 pgvector，而非 PostgreSQL 本身）
- 向量相似度**不需要自己实现**，pgvector 在数据库层面自动计算
- pgvector提供向量距离运算符（如`<=>`余弦距离、欧氏距离等），数据库自动计算相似度并排序

---

### Q5: 为什么情景记忆用PostgreSQL + pgvector，语义记忆用向量数据库？

**A5**: 选型依据是**查询特征 + 数据规模 + 运维成本**，而非单纯"记忆类型"。记忆类型决定查询特征，但语义记忆不一定就要上专用向量数据库。

**情景记忆**：
- 主要查询：时间范围查询（60%）、精确查询（20%）、JOIN关联（10%）
- PostgreSQL优势：时间索引、JOIN优化、复杂SQL
- 向量搜索只占5%，pgvector够用
- 结论：用 PostgreSQL + pgvector，关系查询和向量同库，省去同步成本

**语义记忆**：
- 主要查询：向量相似度搜索（90%）
- **中小规模（千万级向量以内、QPS 中等）：pgvector 同样适用**，且与情景记忆共用同一数据库，避免"关系库 + 独立向量库"双写同步的运维复杂度——这是多数项目的首选
- **专用向量数据库（Pinecone/Milvus/Qdrant 等）只在以下情况才值得引入**：向量规模极大（亿级+）、高并发纯向量检索、需要水平扩展/多租户隔离，或已存在独立向量中台
- 不需要时间查询和JOIN，但这只是"可以选专用向量库"的必要条件，不是充分条件

---

### Q6: 企业实际会存储所有对话吗？如何取舍？

**A6**: 不会"全量进工作记忆"，但会**分层处理**——这是关键区分（加分点）：
- **原始对话日志**：受合规/审计要求，很多企业确实全量归档到数据湖/冷存储（金融 SEC、医疗 HIPAA 等），但这是审计/训练用途，**不是 agent 的实时记忆**
- **agent 工作记忆**：受成本与上下文窗口限制，必须取舍，不能全存

取舍策略（生产常见，数字仅为示意量级，勿当精确事实）：
1. **重要性过滤**：用 LLM 打 importance 分或规则（关键词/用户反馈）只保留关键会话，而非全部
2. **摘要压缩**：LLM 把长会话生成结构化摘要，原文入冷归档，记忆只留摘要，大幅降存储
3. **生命周期清理**：按 retention policy（留存策略，即"数据保留多久"的规则）滚动淘汰（如热数据保留 N 天，N = 业务定的具体天数），控制增长
4. **分层存储**：热数据（Redis/pgvector，低延迟）、温数据（普通 DB）、冷数据（对象存储/S3 归档）
5. **隐私合规**：PII 脱敏、按策略销毁、满足可审计删除（如 GDPR 被遗忘权）

核心权衡：**存储越多召回越高，但成本与延迟上升**——取舍围绕业务 SLA 和合规要求定，不存在统一"降 X%"的固定值

【复习补充 1：生命周期清理的实现方式】
- 清理是运维/维护操作，**不进用户请求主链路**（不能每条消息顺手全表 DELETE，会拖慢响应、锁表）
- 三种生产实现：
  1. **独立定时脚本/调度任务（最主流）**：cron / Airflow / k8s CronJob 凌晨跑 cleanup 脚本，按 retention policy 删过期数据；与业务解耦、失败不影响线上、好监控
  2. **数据库原生命命周期（更省事）**：PG 分区表按天/月建分区，过期直接 `DROP PARTITION`（秒级、不锁表，比 `DELETE` 高效）；部分存储自带 TTL（Redis 过期键、MongoDB TTL 索引），连脚本都不用写
  3. **惰性清理（小项目够用）**：写入时顺手清 / 读取时跳过过期项，简单但不彻底，仅作补充
- 要点：清理逻辑通常单独成离线 job；规模上去后用"分区 drop / DB TTL"替代逐条 DELETE

【复习补充 2：数据分层存储映射（热/温/冷 ↔ 记忆类型 ↔ 介质）】
- 映射关系：

| 层 | 存储介质 | 放什么 | 访问频率 |
|----|----------|--------|----------|
| 热 (Hot) | Redis（进程内 + Redis 会话缓存） | 当前会话即时上下文、最近几轮消息、本次要用的 Top-K 记忆结果 | 毫秒级、每条请求都碰 |
| 温 (Warm) | PostgreSQL + pgvector | 情景记忆（带时间索引的对话历史）+ 语义记忆（偏好/事实向量） | 按需检索，回话级 |
| 冷 (Cold) | 对象存储（S3/OSS）/ 数据湖 | 全量原始对话日志（合规归档）+ retention 过期后从温层滚下的数据 | 极少，审计/复盘/重训才读 |

- 校准点：
  - 热层**不放向量 embeddings**（向量本体留温层 pgvector）；热层只放"这次回复立刻要用的"：近期原文 + 缓存好的 Top-K 召回
  - 温层内部语义记忆（偏好）比情景记忆（某次具体对话）更持久、更热；高频语义可再提一级进 Redis 缓存
  - 数据会"流动"而非静态分层：`新对话 → 热(Redis) → 会话结束/抽取 → 温(PG，保留 N 天) → 过期/归档 → 冷(S3)`，这正是生命周期清理在分层里的落点
- 上线分配量级（示意，非死数字）：热只占极小比例（按并发会话数估，TTL 自动蒸发）；温是体量主体（按 retention 30–90 天封顶，PG 分区控增长）；冷体积最大且只增不减（全量合规归档），必须放最便宜的对象存储，绝不占 PG 空间

### Q7: 语义记忆如何自动化提取？每一轮都调用LLM吗？

**A7**: 不一定要"每轮都调大模型"，但也不是绝对不调——取决于用什么模型、是否阻塞主链路。生产常见混合策略：
1. **规则/模板实时提取**：正则或关键词匹配"我喜欢X""城市：北京"等强信号，零成本、<100ms，适合高精度的结构化偏好
2. **事件/阈值触发 LLM 提取**：出现关键事件（投诉、下单）或上下文缓冲将满（MemGPT 式）时，调用 LLM 抽事实，**异步执行不阻塞回复**
3. **批量/离线抽取与合并**：定时（如凌晨）对当天会话做一次 LLM 抽取，并做**去重与冲突消解**（"之前喜欢A、现在喜欢B"需合并）

加分点：
- 抽取可用小/便宜模型（mini 级或本地模型），per-turn 成本已很低，不必为省成本牺牲质量
- 抽取放异步队列，不抢用户回复延迟
- 语义记忆要持续合并去重，否则堆积重复/矛盾事实

勿给"降95%"等死数字——成本取决于模型选择、调用频率与是否异步，按业务预算权衡

### Q8: 为什么情景记忆主要是时间范围查询，语义记忆主要是相似度搜索？

**A8**: 解决的业务问题不同：

**情景记忆应用场景**：
- 客服回溯："我上周投诉的问题解决了吗？" → 时间范围查询
- 合规审计："查询最近30天的交互记录" → 时间范围查询
- 数据分析："统计过去一周的用户活跃度" → 时间范围+聚合查询

**语义记忆应用场景**：
- 个性化推荐："帮我推荐一款合适的手机" → 检索用户偏好
- 智能客服："我想订机票，有什么需要注意的？" → 检索用户约束
- 智能问答："你们的产品有什么优势？" → 检索用户关注点

### Q9: 情景记忆和语义记忆的触发条件是什么？

**A9**:

**情景记忆触发条件**：
- 用户提及时间（40%）：关键词如"上周"、"昨天"、"最近一个月"
- 回溯历史（20%）：关键词如"上次"、"之前"、"历史"
- 合规审计（20%）：定时任务、审计系统自动触发
- 数据分析（20%）：关键词如"报表"、"统计"、"趋势"

**语义记忆触发条件**：
- 个性化推荐（40%）：关键词如"推荐"、"适合"、"建议"
- 智能客服（30%）：关键词如"注意"、"要求"、"预算"
- 会话启动（20%）：用户登录、会话开始时自动加载用户画像
- 风险预警（10%）：系统自动检测异常行为

### Q10: PostgreSQL和MySQL的区别？MySQL有向量扩展吗？

**A10**:

**PostgreSQL vs MySQL核心区别**：
- PostgreSQL：功能丰富、扩展性强、适合复杂业务
- MySQL：简单易用、性能优先、适合简单业务

**MySQL向量扩展**：
- ❌ 没有官方向量扩展
- ❌ 没有类似pgvector的插件
- ⚠️ 需要第三方方案或应用层实现

**Agent开发推荐**：PostgreSQL + pgvector
- JSONB存储对话历史（支持索引）
- 向量搜索原生支持
- 复杂查询能力强
- 一站式解决方案

### Q11: 工作记忆就是上下文窗口吗？

**A11**: 是的！工作记忆本质上就是模型的上下文窗口管理工具：
- **上下文窗口**：模型能"看到"的对话历史范围（如GPT-4的128K tokens）
- **工作记忆**：负责管理当前对话内容，确保在上下文窗口限制内
- **核心功能**：添加/查询/清理对话历史，受模型窗口大小限制

### Q12: PostgreSQL和pgvector的基本知识？

**A12**:

**PostgreSQL**：开源关系型数据库
- 支持SQL查询、事务、JSONB（二进制JSON）
- 可扩展架构，支持表分区、自定义索引

**pgvector**：PostgreSQL向量扩展
- 添加VECTOR列类型存储向量数据
- 提供相似度运算符：`<=>`(余弦距离)、`<->`(欧氏距离)
- 支持向量索引：IVFFlat（百万级）、HNSW（高性能）

**基础使用**：
```sql
-- 创建向量表
CREATE TABLE items (id SERIAL, embedding vector(1536));

-- 插入向量
INSERT INTO items (embedding) VALUES ('[0.1, 0.2, ...]');

-- 相似度查询
SELECT 1 - (embedding <=> '[0.1, 0.2, ...]') AS similarity FROM items;
```

### Q13: 分层存储（热/温/冷）如何实现？

**A13**: 通过表分区+存储介质分离实现：

**存储介质**：
- **热数据**：最近7天，SSD存储，访问延迟<10ms
- **温数据**：7-30天，HDD存储，访问延迟10-50ms
- **冷数据**：30天以上，对象存储(S3)，访问延迟50-200ms

**实现方案**：
```sql
-- 创建分区表
CREATE TABLE sessions (
    id SERIAL,
    timestamp TIMESTAMP
) PARTITION BY RANGE (timestamp);

-- 热数据分区（SSD）
CREATE TABLE sessions_hot PARTITION OF sessions
    FOR VALUES FROM (NOW() - INTERVAL '7 days') TO (NOW());

-- 温数据分区（HDD）
CREATE TABLE sessions_warm PARTITION OF sessions
    FOR VALUES FROM (NOW() - INTERVAL '30 days') TO (NOW() - INTERVAL '7 days');
```

**自动迁移**：通过定时任务将过期数据迁移到对应存储层

### Q14: "没有银弹"是什么意思？

**A14**: 软件工程概念，指"没有万能解决方案"：
- **核心含义**：没有单一技术能解决所有问题
- **实际应用**：
  - 情景记忆适合PostgreSQL（时间查询为主）
  - 语义记忆适合向量数据库（相似度搜索为主）
  - 小规模项目可用PostgreSQL+pgvector一套系统
  - 大规模项目需分层架构，专业工具做专业事
- **决策原则**：根据具体需求选择技术，权衡成本/性能/复杂度

## 🎯 核心原则总结

1. **根据查询需求选择数据库**：
   - 混合查询场景（时间+向量）→ PostgreSQL + pgvector
   - 纯向量搜索场景 → 专业向量数据库

2. **根据数据特征选择存储方案**：
   - 有时间戳、需要关联 → 传统数据库
   - 无时间戳、独立事实 → 向量数据库

3. **成本控制优先**：
   - 不要存储所有对话（会爆炸）
   - 规则提取 > LLM提取（成本更低）
   - 批量处理 > 实时处理（效率更高）

4. **实用主义**：
   - 没有银弹，根据业务需求选择方案
   - 小规模项目：PostgreSQL + pgvector一套搞定
   - 大规模项目：分层架构，专业工具做专业事

## 🔧 工作记忆落地与上下文压缩（补充讨论）

> 以下基于我们后续关于「工作记忆压缩 / 上下文窗口爆炸 / RAG 入库 / Agent 循环超窗」的讨论整理。同一知识点归并到一处。

### Q15: 工作记忆"只保留最近 k 轮 + 自动摘要旧数据"是主流落地形态吗？怎么实现？

**A15**: 是的。生产里几乎不会纯用 `ConversationBufferMemory`（全存会爆），而是把两种 LangChain 组件结合：
- `ConversationBufferWindowMemory`（只留最近 k 轮） = "最近 k 轮原文"
- `ConversationSummaryMemory` / `ConversationSummaryBufferMemory` = "更早的自动摘要"
- **落地形态**：`上下文 = [历史摘要(1段)] + [最近 k 轮原文]`。`ConversationSummaryBufferMemory` 同时维护"摘要"和"buffer(最近若干轮)"，正好是这种形态。

### Q16: 压缩（摘要）的触发时机是什么？常用哪种方式？

**A16**: 压缩不是"超了才压"，而是"每轮追加后、调模型前做判断"。三种触发方式：
1. **基于 token 计数（最常用/推荐）**：每轮拼完上下文数 token，超过阈值（窗口 60%~80%）就把最老轮次送摘要。直接对齐物理上限，不受单轮长短影响。
2. **基于轮数**：buffer 超 k 轮就压最老的那轮。简单但不可靠（一轮可能很长或很短，和窗口对不齐）。
3. **基于"即将溢出"预判**：估算下次输出会不会超窗，超了先压。更省但复杂，进阶优化才用。
- **结论**：绝大多数落地用方式 1；方式 2 太粗糙很少单用；方式 3 是进阶。

### Q17: 压缩调用的模型能换成小模型吗？LangChain 能自己设置吗？

**A17**: 能，而且这是标准做法——生产摘要几乎都用小模型（如 gpt-4o-mini、本地 7B），不用旗舰模型。
- LangChain 的 memory 组件**接受你传入的 LLM 实例**，模型完全由你指定：
  ```python
  small_llm = ChatOpenAI(model="gpt-4o-mini")   # 小模型做摘要
  memory = ConversationSummaryBufferMemory(llm=small_llm, max_token_limit=2000)
  ```
- 为什么用小模型：摘要对推理要求低，小模型质量足够、便宜约 10 倍、快很多（呼应 Q7「语义提取别每轮调大模型、批量+小模型省 95% 成本」）。

### Q18: 如果单个问题本身就超窗口（第一轮就爆），怎么办？单轮内部会压缩吗？

**A18**: 关键区分：**上下文压缩只解决"历史堆积"，不解决"单份输入过大"**。
- 单轮超窗（如用户贴 200 页 PDF）时，没有"更老的历史"可摘要，压缩历史的机制**无能为力**，也不能压缩"用户刚发的这一整段"（压了就丢了要问的东西）。
- 单轮超窗靠**输入侧预处理**（不是压缩历史）：
  - 输入分块 / 截断：超长输入只送相关段
  - **检索式喂入（RAG）**：长内容存外部，按需召回相关片段（呼应 Q 检索式记忆）
  - 外部工具读取：让子 Agent 读文件、只回传结论（呼应 read-only 子 Agent）
- 工程做法：调模型前加"输入长度检查"，超了就走分块/RAG/子 Agent，而不是硬塞报错。

### Q19: "输入分段"和"检索式喂入"是同一个方法吗？不都是 RAG 吗？

**A19**: 对，两者是同一套 RAG 的前后环节，不是两种独立方法：
- **输入分段（分块）** = RAG 第①步：把长内容切小，否则语义稀、检索不精、塞不进上下文（对应 Q 切分方案）。
- **检索式喂入** = RAG 第③④步：问题 embed → 查 top-K → 只把相关片段送模型。
- 没有分块，检索粒度稀；没有检索式喂入，分块了也白切。两者合起来才是完整 RAG。注意和"硬截断"（无语义匹配、粗暴丢）区分开。

### Q20: 单轮超长走 RAG，算的是"谁和谁"的相似度？向量要存数据库吗？

**A20**:
- **相似度**：永远算「用户的问题向量」vs「内容切出来的每个小片段向量」。不是长内容内部自比，也不是和历史对话比。内容来源（上传文件 / 当场长消息）只影响入库时机，算法完全一样。
- **是否存库**：是的，生产必须先把长内容"切分+embed+入库"才能检索。
  - 上传的文档/知识库：用户一上传，后台**异步预处理**切分+embed+入库，和对话解耦（类似豆包传文件即解析）。
  - 当场贴的长消息：请求内**同步**切分+embed+入库（多花一点延迟，只做一次）。
  - 向量存持久库（跨会话复用）或会话级临时库（TTL 自动清）。

### Q21: 用户删除了上传的文件，对应向量会删掉吗？

**A21**: 会。生产里删文件要**联动按 `file_id` 批量删对应向量**（向量库都支持按 metadata 过滤删除），保持库和文件系统一致，否则库里会残留已删文件、检索可能召回不存在的内容。
- 区分两种生命周期：① 上传的知识库文件 = 持久库，只有主动删文件/retention 策略才清；② 当场长消息的临时库 = 会话结束/TTL 自动清。**不会"一轮对话结束就清持久文件"**。

### Q22: 上传文件向量化入库 / 删除清向量，这些逻辑是硬编码还是写成工具让模型处理？

**A22**: 是**后台服务的硬编码业务逻辑**，不是交给模型当工具处理。
- 上传/删除/向量化是确定性系统操作（读文件、调 embed、写/删库），由用户点击按钮触发后端代码直接执行，不经过模型决策。
- 模型在对话阶段只调"检索工具"去**已建好的库**查，不负责建库/删库。
- 例外：若 Agent 系统允许"对话中临时让 Agent 读某文件"，那"读取并向量化"可封装成工具让 Agent 调（如 read-only 子 Agent）；但产品级"上传知识库文件"是后台预处理，非 Agent 工具。

### Q23: Agent 循环（ReAct：决策-行动-观察）中间消息太多超窗，怎么处理？

**A23**: 这是"第③类超窗"（模型自己多步循环产生 observation 堆积），和"多轮对话累积"不同。生产做法：
1. **工具结果只留结论**：工具返回 8000 字 → 提炼成"查到 3 条相关订单"再写回主上下文（呼应 Q 工具返回压缩）。
2. **子 Agent 隔离取信息**：派 read-only 子 Agent 干重活，原始大结果留在其自身上下文，主 Agent 只收结论（呼应 read-only 子 Agent）。
3. **循环内滚动摘要/截断**：对较早步骤做摘要（机制同源"多轮压缩"，对象是步骤历史）。
4. **步数封顶 + 状态外置**：`max_iterations` 封顶；累计步骤摘要存外部（Redis/DB），主上下文只持当前步+最近几步。
- 若某步 observation 本身超长，可复用 Q18 的 RAG 切分检索。

### Q24: Agent 循环超窗的处理（压缩/切子Agent）需要硬编码吗？模型不知道自己调工具，谁控制时机？

**A24**: 需要硬编码，且控制流在框架。Agent 跑在"循环框架"里：
- **框架封装**：循环结构（while）、解析模型 tool_call、执行工具——这些不用你写（LangChain `AgentExecutor` / LangGraph 已封装）。
- **你要硬编码**：工具返回后怎么处理（留结论/切子Agent）、上下文超阈怎么压——这些框架不管。
- **时机**：工具一返回 → `handle_result` 按工具类型调子 Agent/小模型提炼 → 写回上下文 → 每轮检查 token 超阈就压最早步骤。模型从头到尾只看到压缩后结论，不知道中间被摘要。

### Q25: 是不是"每轮循环行动后就判断 token 是否压缩早期信息"？

**A25**: 大方向对，精确说两点：
- 判断时机在**写回上下文后、下一次模型决策前**（不是行动刚结束——行动拿到的是 raw，还没写进上下文）。
- 压缩对象是**滚动压最早的步骤历史**（不是只压开头），且长工具结果在写回前已被单独压成结论。
- 修正表述：每完成一轮（工具结果处理写回后），框架数总 token，超阈就把最早若干步滚动摘要，保留最近几步原文+一条历史摘要。

### Q26: LangChain 的 AgentExecutor 已封装循环，为什么对话压缩/摘要这些还要我硬编码？

**A26**: 因为**框架只给"循环骨架"，不给"循环内业务处理"**：
- 框架写死的：while 循环、解析 tool_call、执行工具。
- 框架**没**做的（要你写）：① 工具返回后怎么压缩（默认原样拼回）；② 上下文超了怎么压（默认不自动压，需接 memory 组件）；③ 何时调子 Agent。
- 实际接法：工具里写压缩逻辑（`@tool` 内 `summarize_with_small_model`）；给 Agent 配 `ConversationSummaryBufferMemory(llm=small_llm)` 让每轮自动压历史（不接就默认不压）。

### Q27: 中小智能客服（如 LangChain 搭建）需要考虑这些压缩吗？

**A27**: 看规模和形态，不是两套都必做：
- **工具/检索返回压缩（第1块）**：基本都要。客服工具（查订单/查知识库）返回动辄几十条，不压会爆窗+噪声干扰模型。简单场景用"规则裁剪/top-N 格式化"即可，不必小模型。
- **上下文历史压缩（第2块）**：中小短对话（FAQ 3-5 轮）不用；长会话/复杂工单客服应接；纯 RAG 单次问答不涉及（无循环历史）。
- 对照表：

| 客服类型 | 第1块(工具/检索返回压缩) | 第2块(多轮历史压缩) |
|---|---|---|
| 纯 RAG 问答 | ✅ 检索结果裁剪 | ❌ 单次无循环 |
| FAQ 短对话 | ⚠️ 工具短可不压 | ❌ 对话短不爆 |
| 复杂工单多轮 | ✅ 返回压+格式化 | ✅ 接 summary memory |
| 多 Agent supervisor | ✅ 各子 Agent 返回压 | ✅ 主 Agent 历史压 |

### Q28: 为什么压缩分软触发 / 硬顶两档？增量滚动摘要是什么？

**A28**: 单阈值（只在 80% 才压）有两个毛病：① 0~80% 从不压，摘要一直空着，到 80% 要一次滚很多轮、损失大；② 突发超长轮会瞬间从 60% 飙到 100%+，中间没缓冲直接爆窗。两档对应操作系统「低水位 / 高水位标记」：
- **软触发（窗口 60%）**：提前温和介入，把最老轮逐轮滚进「滚动摘要」（LLM 摘要），每次只滚一小撮、留 40% 大缓冲；摘要是**增量累积**的（旧摘要+新轮一起压），不会某天突然从零压一大坨。
- **硬顶（窗口 80%）**：不可逾越的红线，压完必须回落到 80% 以下；只有冲过硬顶、压完保留区仍超时，才连带「单轮兜底」（折叠当前轮内多条结论 / 溢出硬截断 / 更前轮整轮滚摘要）。
- 两档**压缩方法都是小模型 LLM 摘要**，区别只在触发早晚与目标水位（60% 留缓冲 vs 80% 压更狠），与 LangMem 的 early/soft trigger 一致。
- **滚动摘要作为独立字段**（state.summary）承载，不再伪装成 messages 第 0 条的 SystemMessage，可单独预算、单独传递。
