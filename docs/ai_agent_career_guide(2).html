二、分方向学习路线

按你的背景选一条，照阶段推进；每阶段都有明确「产出物」作为里程碑。

① AI Agent 应用开发

适配：零基础 / 转岗 / 本科 ｜ 目标：能独立交付端到端 Agent 应用（最易上手，需求最大）

1 阶段 0 · 基础（1–2 周）
  • Python 异步 + FastAPI 服务端基础
  • 调通 OpenAI / Claude / DeepSeek API（流式·函数调用）
  • Prompt 工程基础：角色·CoT·结构化输出
✅ 产出：能写调用 LLM 的小程序
2 阶段 1 · 入门（3–6 周）
  • LangChain/LangGraph 核心组件（Chain·Tool·Memory）
  • 手搓第一个 ReAct Agent
  • RAG 基础：文档切分 + Chroma 向量库 + 检索
✅ 产出：一个带知识库的问答 Agent
3 阶段 2 · 进阶（7–12 周）
  • Tool Calling + 自写 MCP Server 接入真实工具
  • 多智能体协作（CrewAI / AutoGen）
  • 可观测：LangSmith 跟踪与评估
✅ 产出：能调用外部系统的多步 Agent
4 阶段 3 · 独立交付（13–24 周）
  • 端到端项目（智能客服 / 竞品分析 / 研报生成）
  • Docker/K8s 部署 + CI/CD
  • GitHub 作品集 + 技术博客复盘
✅ 产出：2–3 个可演示项目，达到独立交付水平

② Agent 框架 / 核心研发

适配：硕士 / 算法 / 高薪 ｜ 目标：研发决策算法、框架与执行引擎（天花板最高）

1 阶段 0 · 基础（1–3 月）
  • 扎实 CS：算法·分布式·网络·操作系统
  • Python + C++/Rust 双语言
  • Transformer/Attention 原理精读
✅ 产出：能读源码、写高性能模块
2 阶段 1 · 原理（3–6 月）
  • RLHF/DPO 对齐；MDP 决策理论
  • 精读 LangGraph / AutoGen 源码
  • 自研轻量 Agent 循环（ReAct/Reflexion）
✅ 产出：理解框架底层而非调 API
3 阶段 2 · 深入（6–12 月）
  • 多智能体协作理论（博弈·任务分配·通信）
  • 长链路稳定性：ToT·自我反思·回滚重试
  • 推理优化：量化/蒸馏/KV-Cache
✅ 产出：可改进框架核心模块
4 阶段 3 · 产出（12月+）
  • 复现顶会论文并工程化
  • 向开源框架提 PR / 自研框架
  • 技术博客 + 性能 Benchmark
✅ 产出：有影响力的开源/论文贡献

③ 多智能体解决方案架构（ToB）

适配：技术 + 业务复合 ｜ 目标：面向企业设计落地方案、打通系统、做交付

1 阶段 0 · 入门（1–4 周）
  • 低代码平台 Coze / Dify 搭一个内部 Bot
  • 理解业务流程拆解与原子化
  • 企业 RAG 知识库调优
✅ 产出：部门级自动化小工具
2 阶段 1 · 方案（1–3 月）
  • 企业方案设计：定义智能体角色与协作流
  • 系统集成：ERP/CRM/飞书/企业微信
  • MCP 打通内外数据
✅ 产出：一套企业方案模板
3 阶段 2 · 交付（3–6 月）
  • 多智能体编排与 ROI 评估
  • 售前 POC + 技术交流
  • 项目管理与客户预期管理
✅ 产出：可主导中大型交付
4 阶段 3 · 专家（6月+）
  • 垂直行业深耕（金融/法律/制造）
  • RPA + Agent 深度融合
  • 行业方法论沉淀与培训
✅ 产出：行业壁垒 + 客户案例

④ Agent Infra / 平台工程

适配：底层 / Rust·C++ / 分布式 ｜ 目标：构建 Agent 运行底座（引擎·推理·向量·网关）

1 阶段 0 · 基础（1–3 月）
  • Rust/C++ + 分布式系统 + 异步 IO
  • Docker/K8s 容器编排
  • GPU 推理基础
✅ 产出：能写高性能服务
2 阶段 1 · 引擎（3–6 月）
  • 推理加速：vLLM / 量化（GPTQ/AWQ）
  • 向量检索算法：HNSW/IVF/ANN
  • 可观测体系：Trace/Metrics/日志
✅ 产出：自研推理或检索组件
3 阶段 2 · 平台（6–12 月）
  • MCP 网关 / 服务市场 / 权限管控
  • 算力调度·负载均衡·弹性扩缩
  • 成本管控·限流降级
✅ 产出：Agent 运行底座原型
4 阶段 3 · 规模（12月+）
  • 支持大规模并发的 Agent 平台
  • 开源贡献 / 内部基建落地
  • 性能 Benchmark 与调优
✅ 产出：平台级工程能力

✅ 产出：可信 Agent 体系

一、Agent 基础与核心循环
01Agent 是什么？与传统 LLM 链式调用 / 普通 Chatbot 的本质区别？
把 Agent 想成会自己想办法干完活的实习生。周五下班前你跟实习生说：「下周一到周二上海有雨，把这两天的室外团建取消、改到三楼会议室，并通知所有报名的人。」他不会等你一步步下指令，而是自己：查天气预报 → 判断要不要改 → 翻出会议邀请 → 改地点 → 群发通知 → 回头跟你说「搞定」。这就是 Agent。 对比一下：Chatbot 像问答机，你问「团建取消流程怎么走」，它只给你讲概念；LLM 链式调用（Chain） 像流水线工人，你把所有步骤写死，他一步不差照做，但不会自己转弯；Agent 的核心是「给目标，它自己闭环干完」——条件不满足就停，满足就一路做到底。
面试怎么答（技术内核）
  • 一句话定义： Agent = 一个会循环「思考→行动→观察→反思」的 LLM 程序，能自己决定调哪个工具、走几步，而不是你写死流程。
  • 四个零件： ① 大脑（LLM，负责规划和判断）；② 记忆（Memory，记住上下文和过往）；③ 手脚（Tools，能查资料、跑代码、发消息）；④ 循环（反复「想→做→看」，直到干完）。
  • 本质区别 = 闭环 + 自主决策。 Chatbot 是「一问一答」；Chain 是「你定死路径」；Agent 是「运行时由模型动态决定下一步」，所以它能应对没预料到的状况。
  • 对比例子： 任务「明天下雨就取消下午的会并通知大家」。Chatbot 只解释概念；Chain 机械地「查天气→取消→通知」硬走；Agent 先查天气、判断要不要取消、再找会议和参会人、发通知，若不下雨就什么都不做。
避坑 / 拓展
  • Anthropic 把用法分成两类：workflow（你用代码写死路径，可控、好调试）和 agent（让 LLM 在运行时动态决定流程和工具，灵活但更难控）。多数产品是两者的混合。
  • 别过度设计： 很多需求「把单次 LLM 调用 + 检索/示例」优化好就够，只有真的需要模型自主决策时才上 Agent。

🔑 一句话记住：给目标，它自己闭环干完——这就是 Agent 和「你一步步教」的本质差别。

# Agent 的最小抽象：LLM + 记忆 + 工具 + 循环
class Agent:
    def __init__(self, llm, tools, memory):
        self.llm, self.tools, self.memory = llm, tools, memory

    def run(self, goal):
        while not self.memory.done:                 # 未干完就继续循环
            step = self.llm.plan(self.memory.context, goal)  # 思考：下一步干啥
            obs  = self.tools[step.action](**step.args)      # 行动：调用工具
            self.memory.append(step, obs)                   # 观察：记回记忆
        return self.memory.final_answer              # 干完返回最终答案
02描述 Agent 的核心循环（Agentic Loop / ReAct），如何用代码实现最朴素的 Agent？
Agent 干活就是不停地「想→做→看」三步走循环，像人解一道题：先在脑子里想这一步该干嘛（Thought），再动手选个工具并填好参数（Action），看看工具返回了啥（Observation），然后基于结果想下一步，直到觉得干完了输出答案，或者步数到上限就停。这整套套路就是 ReAct（Reason + Act）。 最朴素的代码长这样：一个 while 循环，里面反复「让 LLM 出 thought+action → 你的代码去执行那个工具 → 把结果塞回给 LLM 看 → 判断是否结束」。
面试怎么答（技术内核）
  • ReAct = Reason + Act，标准四步： Thought（思考这步干啥）→ Action（选工具+填参数）→ Observation（工具返回结果）→ 循环，直到输出 Final Answer 或达到 max_steps。
  • 最朴素实现： 一个 for 循环，里面让 LLM 产出 thought 和 action，你的代码执行工具，把结果追加进历史，再喂回 LLM。
  • 三个工程细节不能少： ① 明确的「停止条件」（出现 Final Answer 或步数到顶）；② 步数上限（防死循环）；③ 每轮把历史拼回上下文喂给 LLM，它才能「看到」之前做了啥。
  • 为什么是「循环」而不是一次函数调用： 因为很多任务一步算不出来（比如要查完再判断再通知），循环让 Agent 能根据上一步的真实结果决定下一步。
避坑 / 拓展
  • 纯 ReAct 的坑：死循环、调错工具、参数解析失败。生产必须加 max_iterations、token 预算、重复检测（连续相同动作就强制停）、异常兜底。
  • 用 Pydantic / JSON Schema 约束工具参数，避免模型吐出无法解析的调用——这是最常见的线上 bug 来源。

🔑 一句话记住：Agentic Loop = 不停地「想→做→看」，直到干完或步数到顶。

💻 深度版 · 可运行伪代码
def react_agent(llm, tools, question, max_steps=10):
    history = [f"Q: {question}"]
    for step in range(max_steps):
        out = llm(history)                       # 期望输出 Thought + Action(JSON)
        if out.is_final:
            return out.answer                     # 终止条件：出现最终答案
        try:
            obs = tools[out.tool](**out.args)     # 执行模型选中的工具
        except Exception as e:
            obs = f"ERROR: {e}"                    # 异常兜底，别让循环崩
        history.append(
            f"Thought:{out.thought}\n"
            f"Action:{out.tool}({out.args})\n"
            f"Observation:{obs}"
        )
    return "达到步数上限，未得出最终答案"        # 护栏：绝不无限循环
03ReAct、Plan-and-Execute、Reflection、Tree-of-Thoughts 各适合什么场景？
这四种是 Agent「动脑方式」的四种流派，就像做同一道菜的不同做法： ① ReAct = 边想边做（边炒边尝）；② Plan-and-Execute = 先列好菜谱再下厨（先规划再干）；③ Reflection = 做完自己尝一口挑毛病再改（自我反思）；④ ToT（Tree of Thoughts） = 一次同时试好几条做法、哪条好吃走哪条（最费钱，但最稳）。
面试怎么答（技术内核）
  • ReAct： 边想边做，适合需要实时工具反馈的简单多步任务（如查天气再决定）。灵活但难干预。
  • Plan-and-Execute： 先产出全局 plan，再逐步执行。适合复杂、可拆分的任务，而且计划能让人先审一遍（HITL）。plan 过期了还能动态重规划。
  • Reflection： 让 Agent 自我批评后修订，适合写代码、写长文等「质量敏感」任务，能明显提升成品质量。
  • ToT（Tree of Thoughts）： 一次展开多条思路、用搜索（BFS/DFS）选最优，适合需要探索搜索空间的难题（如数学推理），但 token 成本高、速度慢。
避坑 / 拓展
  • 实战常组合： 先用 Plan 出骨架 → ReAct 执行子步骤 → Reflection 收口。一套组合拳比死磕单一模式效果好。
  • Anthropic 建议从最简单的模式起步（如 prompt chaining / routing），别一上来就搭复杂 Agent。复杂度是按需加的。

🔑 一句话记住：四种动脑流派：边做边想 / 先计划 / 做后反思 / 多路试错——按任务复杂度选。

二、工具调用与开放协议（Function Calling / MCP / A2A）
04Function Calling / Tool Calling 是什么？模型怎么决定调哪个工具、参数怎么传？
Function Calling 就是让模型「开口要调用某个函数并填上参数」，但模型自己不执行。比如它输出一段结构化 JSON：「我要调 search(query='北京明天天气')」，你的代码去真查天气，再把结果喂回去。模型靠你给的「工具说明书」（JSON Schema）来决定调谁、怎么填——就像你给实习生一本《公司能用的系统操作手册》，他照着手册决定用哪个系统、填什么。
面试怎么答（技术内核）
  • 机制： 你每次请求时把 tools 的 schema（名字、用途、参数格式）一起发给模型；模型判断「要不要调、调哪个、参数填啥」，输出结构化调用请求；你的代码执行后把结果（Observation）再喂回模型。
  • 模型怎么选工具： 完全看你写的工具 description 写得好不好。描述模糊，模型就选错或瞎编。所以「工具说明书」是工程里最值得花时间的地方。
  • 参数哪来的： 来自模型对当前对话上下文的理解。比如用户说「查北京天气」，模型就从上下文抽出「北京」填进 location 参数。
  • 为什么用 JSON Schema 校验： 模型吐出的 JSON 可能不合法，必须校验、必要时让它重填，否则代码一执行就崩。
避坑 / 拓展
  • 工具太多会撑爆上下文、还容易选错——按场景分组，限制单次「可见工具数」（比如一次只给 8 个），用路由先粗筛再给细工具。
  • 有团队在工具描述里加 usage_example + edge_cases，把调用准确率从六七成提到 90%+。把说明书写细，比换更大的模型还管用。

🔑 一句话记住：Function Calling = 模型「开口要调函数并填参」，你的代码去真执行。

💻 深度版 · 可运行伪代码
import json

def handle_tool_call(llm, tools, user_msg):
    tools_schema = [t.schema() for t in tools]        # 把「工具说明书」给模型
    resp = llm.chat(user_msg, tools=tools_schema)
    if resp.tool_call:
        fn   = tools[resp.tool_call.name]             # 按名字找到真实函数
        args = json.loads(resp.tool_call.arguments)   # 模型给的参数（需校验）
        result = fn(**args)                           # 你的代码真执行
        return llm.chat(user_msg, tools=tools_schema,
                        tool_result=result)           # 结果喂回模型
    return resp.content                               # 不需要工具就直接答
05MCP 是什么？解决什么问题？和 Function Calling 的关系？
没有 MCP 之前，每接一个数据源（数据库、Git、Slack…）你都得为每个 AI 应用单独写一套对接代码——N 个应用 × M 个工具 = N×M 个对接，又烦又重复。MCP 相当于给 AI 生态定了根「统一插头标准」，被官方类比为 AI 的 USB-C：工具方按标准做「服务器」，应用方按标准做「客户端」，两边各写一次就能互通，复杂度从 N×M 降到 N+M。
面试怎么答（技术内核）
  • 是什么： 由 Anthropic 于 2024-11 开源的开放标准，统一了「Agent ↔ 工具/数据源」的连接方式。你不用再为每个工具写私有对接。
  • 三大原语： ① Tools（可执行的动作，如「查数据库」）；② Resources（可读取的数据，如「某文件内容」）；③ Prompts（预置的提示模板）。
  • 传输方式： 基于 JSON-RPC 2.0；本地进程间用 stdio，远程用 Streamable HTTP（早期是 SSE，现已演进为 Streamable HTTP）。
  • 和 Function Calling 的关系（重点题）： MCP 是「协议层」——负责工具的发现、描述、路由；Function Calling 是「机制层」——模型请求执行某个函数。简单说：FC 发生在 MCP 内部，MCP 让 FC 标准化、可复用。
避坑 / 拓展
  • MCP 不替代 REST API，而是把 REST/DB/文件系统包成统一接口，让 Agent 即插即用。
  • 安全仍是你自己的责任： MCP 协议不管授权/审计，你暴露一个连数据库的 MCP Server，连接串、权限、审计日志都得自己加。协议不替你做安全。

🔑 一句话记住：MCP = AI 的 USB-C 统一插头，让工具一次写好、处处可用。

06A2A 协议是什么？与 MCP 的区别？
如果 MCP 解决「Agent 怎么用工具（纵向）」，那 A2A 解决「Agent 怎么跟另一个 Agent 打交道（横向）」。想象每个 Agent 有张电子名片（Agent Card），写明自己会什么、怎么联系；想合作的 Agent 读了名片就能派任务、盯进度。由 Google 于 2025-04 提出，现由 Linux Foundation 治理，获 Google、IBM、Salesforce、SAP 等众多企业支持。
面试怎么答（技术内核）
  • 是什么： A2A（Agent2Agent）是 Google 2025-04 提出的开放协议，解决不同厂商/框架的 Agent 之间「互相发现、委派任务、流式通信」。
  • 核心三件套： ① Agent Card：通常在 /.well-known/agent.json，描述能力/技能/认证方式；② Task 生命周期：submitted → working → input-required → completed/failed；③ 传输：JSON-RPC 2.0 over HTTP(S)，长任务用 SSE 流式推送进度。
  • 和 MCP 的关系（必考题）： MCP = Agent↔Tool（纵向，用工具）；A2A = Agent↔Agent（横向，找同伴）。生产栈常两者并用：Agent 通过 A2A 找到同伴，通过 MCP 调用工具。
避坑 / 拓展
  • A2A 不适合简单确定性操作——那种直接调固定 API 更省事，别为了用协议而用协议。
  • 治理现状： 已由 Linux Foundation 治理（这是它和「某大厂私有的东西」最大的区别，意味着中立、可长期依赖）。

🔑 一句话记住：MCP 是 Agent 用工具，A2A 是 Agent 找同伴——一个纵向一个横向。

def delegate(peer_url: str, skill: str, text: str):

    assert skill in card["skills"]                     # 确认对方能干这活

    # 2) 派发任务，进入 Task 生命周期

                         json={"skill": skill, "input": text}).json()

    while task["status"] not in ("completed", "failed"):
        task = requests.get(f"{peer_url}/tasks/{task['id']}").json()
    return task.get("artifact")

07多智能体有哪些常见拓扑？各自优劣？
多个 Agent 怎么配合，常见几种「队形」，就像公司里不同协作方式： ① 总控型（Supervisor）：一个主管派活，像项目经理，好管控但主管容易成瓶颈；② 黑板/群聊型：大家围着一块共享白板写，灵活但容易乱、事后难追溯谁说了啥；③ 流水线型：一个接一个传下去，简单可预测但慢；④ 层级型：大主管→小专家，适合大任务层层拆解。
面试怎么答（技术内核）
  • ① Supervisor/Orchestrator（中心化调度）： 可审计、易管控，但单点瓶颈、主 Agent 易过载。是面试最高频考点。
  • ② 群聊/黑板（共享黑板或消息总线）： 去中心、灵活，适合探索性协作，但易循环、难追溯谁做的决策。
  • ③ 流水线/Pipeline（顺序传递）： 简单可预测，适合步骤固定的任务，但串行慢、一步卡住全卡。
  • ④ 层级（Manager → Specialist）： 大主管拆任务、小专家各管一摊，适合大任务，但要注意上下传信息的损耗。
避坑 / 拓展
  • 通信建议只传「结论」而非全量上下文，否则上下文会爆炸；用 Agent Card / 状态快照表达数据依赖。
  • 面试能清晰讲出 Supervisor 模式（一个主控 + 多个专职子 Agent，主控只调度不写业务）基本就能覆盖大部分多智能体提问。

🔑 一句话记住：多智能体四种队形：主管派活 / 围着白板 / 流水线 / 层级——控与活的取舍。

08如何设计多智能体系统解决复杂任务？如何划分 Agent 职责？

面试怎么答（技术内核）
  • 主-从编排 + 动态路由： 主控只做意图识别 / 任务拆分 / 汇聚，绝不写业务逻辑；子 Agent 封装特定能力（独立 prompt + 工具 + 知识库）。

  • 用 A2A / LangGraph 编排： 让职责边界清晰、流转可追踪，而不是把所有逻辑塞进一个超长 prompt。

避坑 / 拓展
  • 故障隔离： 子 Agent 失败要返回结构化错误，主控决定重试 / 绕过 / 转人工，别让一个部门出错拖垮全公司。
  • 跨进程时序错位 用全局状态管理器 + 任务依赖图解决——谁依赖谁的结果，先等人家干完再动。

09什么时候该用多智能体，什么时候不该（Cognition《Don't Build Multi-Agents》）？
业界有个重要反思：Cognition（做 Devin 的团队）2025-06 发文《Don't Build Multi-Agents》，核心结论是——多 Agent 听起来很美，但 2025 年实战里它经常更脆弱。根因是「决策分散 + 上下文难共享」：几个 Agent 各想各的，容易互相矛盾。 文章用「做 Flappy Bird 克隆」举例：一个子 Agent 把背景做成超级马里奥风，另一个做的鸟完全不对味，最后合不拢、incoherent。所以结论很反直觉：默认就用单线程单 Agent，把完整上下文和完整执行轨迹（trace）都给它。
面试怎么答（技术内核）
  • 多 Agent 真正成立的价值只有两点： ① 并行——仅限真正互相独立的「只读」任务（如同时查 5 个资料源），且受阿姆达尔定律上限，并行收益有限；② 隔离——刻意让某些上下文不互通，比如让批评者看不到作者的私密推理，避免「橡皮图章」式敷衍点赞。
  • 代价： token、延迟、协调开销成倍放大，且容易出现「级联失败」和上下文不一致。
  • 关键认知： Cognition 原文没有给出「多 Agent 是单 Agent 的 N 倍成本」这种具体数字，它的论点本质是可靠性——多 Agent 更脆弱，而不是单纯更贵。面试别乱背倍数，讲「脆弱性」才专业。
避坑 / 拓展
  • 写密集型 / 有状态任务（写代码、做游戏） 用多 Agent 反而因「隐式决策冲突」而 incoherent（就是上面 Flappy Bird 的例子）。
  • 原则：默认单 Agent；只有当任务形状明确需要并行或隔离时才拆。 多 Agent 一定放大成本，但更该警惕的是可靠性问题。

🔑 一句话记住：默认单 Agent；只有真要并行或隔离时才拆——多 Agent 更脆弱。

10Agent 的 Memory 怎么设计？短期 / 长期记忆区别与实现？
Agent 的「记忆」分两种，就像人脑： 短期记忆 = 你当下正在聊的工作台，受上下文窗口限制，太长了记不住，得靠「摘要压缩」瘦身； 长期记忆 = 它的笔记本 / 档案库，跨会话保存，又分三小类：记「发生过啥」的情景记忆、记「你是谁 / 你偏好啥」的语义记忆、记「怎么干活」的程序性记忆（比如 Claude 的 CLAUDE.md 那种技能模板）。
面试怎么答（技术内核）
  • 短期记忆 = 当前对话上下文，受窗口限制，用滑动窗口 / 摘要压缩（把旧聊天提炼成关键事实再存回去）。
  • 长期记忆 = 持久化存储，三类： ① 情景记忆：对话历史 → 向量库（如 Milvus），按语义找回；② 语义记忆：用户事实 / 偏好 → 知识图谱或结构化库；③ 程序性记忆：Skills / 工作流模板（如 Claude.md、系统提示里的固定流程）。
  • 为什么区分： 短期解决「这次对话别忘」，长期解决「下次还认得你」。两者实现方式完全不同（一个在上下文里，一个在外部存储）。
避坑 / 拓展
  • 长对话记忆会在接近注意力窗口时退化，要在 10 / 50 / 100 / 200 轮做评估并设置摘要压缩点，别等它「失忆」才处理。
  • 参考资源： 本报告 B站资源里有「唐国梁对比的 5 大 Memory 项目」「Hermes 四层记忆架构」，想深挖可去看。

🔑 一句话记住：短期在上下文里会忘，长期存外部库（情景/语义/程序）跨会话记。

11RAG 在 Agent 里处于什么位置？Agentic RAG 与普通 RAG 区别？
普通 RAG 像「你问一次、它查一次资料、答一次」的图书管理员；Agentic RAG 把「查资料」变成 Agent 手里的工具——它自己决定什么时候查、查几遍、怎么把问题改写得更好查。检索从「被动响应」变成了「Agent 主动决策的事」。比如你问「对比 A 和 B 两家公司的风险」，Agent 会先查 A、再查 B、再针对缺口补查，来回好几轮。
面试怎么答（技术内核）
  • RAG 被「工具化」为 Retriever Tool：Agent 按需、多轮、主动调用（自己决定何时查、查几次、怎么改写 query）。
  • 普通 RAG = 一次检索 + 一次生成，被动的「请求-响应」；Agentic RAG = 把检索「决策化」，模型控制检索时机和次数。
  • 额外好处： 检索还能用于 Skills Discovery——把成百上千个技能描述向量化，Agent 语义检索动态激活，缓解上下文爆炸。
避坑 / 拓展
  • chunk 大小 / 重叠要权衡：太大召回不精、太小丢上下文；embedding 要匹配你的语种 / 领域，这决定了召回上限。
  • Agentic RAG 不是银弹： 简单问答用普通 RAG 就够了，别为了炫技上 Agent 反而变慢变贵。

🔑 一句话记住：普通 RAG 你问它查一次；Agentic RAG 把查资料变 Agent 主动决策的工具。

12RAG 召回质量怎么优化（分块 / 向量 / 混合检索 / 重排）？
想让检索更准，三板斧（就像找资料又快又准）： ① 切分得当：中文按标点递归切，用「父子块」——小块用于精确匹配、大块用于补充上下文（先命中小块，再连同大块一起喂给模型）；② 混合检索：向量语义搜（懂意思）+ 关键词 BM25（懂精确词）互补，再用 RRF 融合排序；③ 重排：用 cross-encoder 精排 Top-K，把最相关的顶上来（粗排后精排，类似先海选再终选）。
面试怎么答（技术内核）
  • 分块： 中文递归标点切分 + 父子块（父块约 1200 token / 子块约 400 token），并给每块注入多级元数据（来源、时间、章节），方便过滤。
  • 混合检索： 稠密向量（HNSW 索引）+ 稀疏 BM25，两套结果用 RRF（倒数排名融合）合并，兼顾「意思对」和「词对得上」。
  • 重排： 用 cross-encoder（如 BGE-Reranker）对粗排的 top-k 精排，把最相关文档顶上来，这是提升「答得准」的关键一步。
  • 评估分层： 检索看 Recall@K / MRR；生成看 Faithfulness / Answer Relevancy。先量再改。
避坑 / 拓展
  • 加语义缓存层（Redis + Sentence-BERT）拦截高频问法，直接返回答案降延迟。
  • 领域自适应微调 Reranker 能提升 Hit@3；但微调前先确认你的数据量够，否则不如用现成模型。

🔑 一句话记住：召回三板斧：父子块切分 + 向量/BM25 混合 + cross-encoder 重排。

13幻觉怎么产生、怎么缓解？
幻觉就是模型「一本正经地编」。比如你问「公司去年差旅费多少」，它没这数据却硬编个「230 万」。成因三类：① 训练数据里没这知识（分布外）；② 你给的上下文不全；③ 它太自信「猜也要答」。缓解的核心思路就一句：给它真证据 + 让它学会说不知道 + 用指标盯住它。
面试怎么答（技术内核）
  • 成因三类： 训练分布外 / 上下文缺失 / 过度自信（即使不确定也要给答案）。
  • 缓解手段： ① RAG 补真证据（让答案有出处）；② 要求「引用出处」，答不出就引不出；③ temperature 调低，减少胡编；④ 明确允许「不知道就说不知道」；⑤ 用 faithfulness 指标监控线上幻觉率。
  • Agent 场景更要注意： 工具返回的结果可能被 Agent 忽略或被篡改，要可溯源——哪句话来自哪个工具结果，能查到。
避坑 / 拓展
  • 生产硬规则： 幻觉率上升就不发布，把它当上线门槛（和准确率、延迟一样重要）。
  • 别只靠 prompt 说「别瞎编」——结构上要「证据驱动 + 指标监控」双保险，prompt 拦不住分布外知识。

🔑 一句话记住：幻觉=编答案；治法是给真证据、允许说不知道、用指标盯。

14如何让 Agent 具备「规划（Planning）」能力？显式 vs 隐式？
规划就是让 Agent「先想清楚再动手，还是边做边想」。 显式规划 = 先列计划再执行（Plan-and-Execute），适合复杂任务，还能在关键节点让人审批（比如「我打算这么干，你同意吗」）； 隐式规划 = 边想边做（ReAct），灵活但难干预，干到一半你插不进话。
面试怎么答（技术内核）
  • 显式规划： 先输出 plan（如 1.查天气 2.若雨则改地点 3.通知），再逐步执行。可在 prompt 中要求输出结构化 plan。适合复杂、可审计任务。
  • 隐式规划： 边想边做（ReAct），灵活、启动快，但中途难干预。
  • 复杂任务建议： 先 plan + 后 reflection；plan 能让人工在关键节点审批（HITL），但 plan 也可能过时，需允许动态重规划。
  • ToT 适合搜索空间大的难题（多分支试错），但贵。
避坑 / 拓展
  • 显式的代价： plan 写错会带着 Agent 走偏，所以要允许「执行中发现不对就重规划」，别把计划当圣旨。
  • Anthropic 建议从最简单模式起步，规划是「按需加的复杂度」，不是默认就要。

🔑 一句话记住：显式=先列计划再干（可审批）；隐式=边做边想（灵活难控）。

15如何实现 Human-in-the-loop（人在回路）？LangGraph 里怎么做？
人在回路就是「在危险操作前先问人」。比如 Agent 要删库、要发钱、要对外发邮件——这种事不能让它自作主张，先暂停等人工点「批准」再继续。LangGraph 用 interrupt() + checkpoint 实现：把当前进度存盘 → 暂停 → 人审批 → 从断点接着跑，不用从头重来。就像你审批 OA 流程，批完继续走，不重填。
面试怎么答（技术内核）
  • 做法： 在流程里插入「等待人工审批」节点，放在敏感写操作 / 高风险决策之前暂停。
  • LangGraph 实现： 用 interrupt() / checkpoint——保存当前状态 → 暂停 → 人工 approve → resume 从断点继续，不重跑前面步骤。
  • 为什么需要 checkpoint： 长链路不是一次函数调用，一旦挂了要能从断点恢复、能介入、能审计，否则一挂就全链路重来。
避坑 / 拓展
  • 高频追问： 「为什么不用普通日志？」「线上挂了怎么恢复？」——答案都是「要能从断点恢复 + 可审计 + 可介入」。普通日志只能看，不能让流程从中间接着走。
  • durable execution / persistence / threads 是生产级 Agent 的标配，不是可选项。

🔑 一句话记住：危险操作前先问人；LangGraph 用 interrupt+checkpoint 断点续跑。

    g.add_edge("approve", END)

16如何评估一个 Agent 的好坏？指标与框架？
怎么判断一个 Agent 好不好？从三个角度打分，就像考核一个员工： ① 结果好不好（任务做成没、约束满足没）；② 过程对不对（工具调对没、步数合不合理，别绕 20 步才搞定）；③ 跑得贵不贵（延迟、token、安全合规）。 工具上用 RAGAS、LangSmith 等做自动评测，把这套考核常态化。
面试怎么答（技术内核）
  • 三维度指标： ① 结果：任务成功率 / 约束满足率 / 人工满意度；② 过程：工具调用准确率、轨迹质量 / 步数；③ 运行：延迟 P50/P95、token/成本、安全合规。
  • 常用框架： RAGAS、LangSmith、DeepEval、Phoenix、OpenAI Evals、AgentBench / GAIA（基准榜单）。
  • span-level tracing： 记录每步 thought/tool/返回/token，出问题时能定位「是哪一步抽风」。
  • LLM-as-judge： 用「另一个模型」当评委打分，且最好用不同模型评（别用生成答案的那个模型自评，会护短）。
避坑 / 拓展
  • RAGAS 没有万能阈值（重点）： 常见目标 faithfulness ≥ 0.85（医疗/法律等安全敏感场景才要求 ≥ 0.90）、answer relevancy ≥ 0.80、context precision ≥ 0.70、context recall ≥ 0.75；先用 golden set 校准再设发布门槛，别直接抄别人的数字当铁律。
  • 评估要分层：检索层和生成层分开看，否则不知道是「没查到」还是「查到了没用好」。

🔑 一句话记住：评估三维度：结果 / 过程 / 成本——RAGAS 没有万能阈值，先校准。

面试怎么答（技术内核）

18Agent 成本和延迟怎么优化？
Agent 很烧钱烧时间（多步调用、反复查工具），省钱省时间的招： ① 模型路由：简单问题用小便宜模型、难的才上大模型（像小病去社区医院，大病才去三甲）；② 缓存：重复问题直接返回缓存答案，能拦掉相当比例请求（常见 20–40%）；③ 压缩 / 并发 / 本地小模型：长上下文压一压、能并发就并发、敏感场景用本地 7B 小模型替代云端 API。
面试怎么答（技术内核）
  • 模型路由： 简单任务用小/便宜模型，复杂才上大模型，避免「杀鸡用牛刀」式烧钱。
  • 语义缓存： 拦截高频问法（占比视业务重复度，常见 20–40%），命中直接返回，降延迟又省钱。
  • 结果/上下文复用 + 并发批处理 + 长上下文压缩，减少重复计算和多余 token。
  • 本地小模型： 用 vLLM 量化部署 7B 本地模型，可把 P95 从 30s 降到 10s 量级（视场景）；多智能体会在 token/延迟/协调上成倍放大开销，要设总预算 / token 上限。
避坑 / 拓展
  • 优化前先量： 用 trace 找出最耗 token / 最慢的那一步，别瞎优化——通常 80% 成本来自 20% 的步骤。
  • 延迟敏感场景优先单 Agent + 缓存，多 Agent 的协调开销会拖慢首响。

🔑 一句话记住：省钱省时：路由用对小模型、缓存拦重复、压缩并发本地化。

19Agent 生产「死循环 / 无限调用工具」怎么办？
Agent 有时候会「卡住」——比如反复调同一个工具、或者绕圈停不下来（像导航把你导进环岛转圈）。治法就是给它上几道「护栏」：步数封顶、token 预算、检测「连续三次干一样的事就强制停」、超时就熔断，并在 prompt 里让它每步自问「这步真的必要吗」。
面试怎么答（技术内核）
  • 硬护栏： 设 max_iterations / token 预算；无意义重复检测（连续 3 次相同 action 强制停）；超时熔断。
  • 软护栏： 元认知指令让 Agent 每步自问「这步真的必要吗」，减少无效循环。
  • 终止条件要清晰： 什么算「干完了」要有明确判断（如「已给出 Final Answer」或「工具返回表示无需继续」）。
避坑 / 拓展
  • 更要治根因： 循环常源于任务描述模糊、或工具返回不可解析（模型看不到「成功」就一直重试）。要在 prompt 和工具 schema 上修根因，而非只加限制。
  • 重复检测别太激进（比如允许重试 2 次），否则正常「重试失败工具」也会被误杀。

🔑 一句话记住：死循环治法：步数封顶+重复检测+超时熔断，并治根因。

        if out.is_final:
            return out.answer                     # 终止条件
        # 连续 3 次干一样的事 → 强制停（防死循环）
        if (out.tool, out.args) in seen[-2:]:
            break
        seen.append((out.tool, out.args))
        try:
            history.append(call_tool(out))        # 正常执行
        except TimeoutError:
            break                                 # 超时熔断
    return "已触发步数/重复护栏"                   # 永不无限循环
20如何提升 Agent 回答的「确定性 / 可复现性」？
有时候你要 Agent 回答「可复现」——同样输入得到同样输出，比如算金额、生成 SQL、抽字段。但 LLM 本身有随机性，所以得「锁死随机 + 强约束结构 + 把确定性的活交给代码」。 举例：让模型生成「查询北京订单的 SQL」，你设 temperature=0、要求输出固定 JSON 格式、并且真正执行 SQL 的是你的代码而不是模型——这样同输入必同输出。
面试怎么答（技术内核）
  • 锁随机： temperature = 0（或极低）、固定 seed（若模型支持）。
  • 强约束输出： 用 JSON / Pydantic schema 约束，避免格式漂移导致解析不一致。
  • 确定性步骤交给代码： 金额计算、SQL 执行、正则抽取这类「算数/规则」活，用普通函数做，别让 LLM 算——它算着算着就飘了。
避坑 / 拓展
  • 完全确定性会牺牲灵活性：要评估「哪些步骤必须确定」（金额/SQL/字段抽取）哪些可概率（措辞/总结）。
  • RAG 引用 + 结构化输出 能同时提升可复现与可审计——答案能追到来源。

🔑 一句话记住：可复现=锁随机+强约束+确定活交给代码，别让模型算数。

21LangGraph 核心概念：StateGraph、Node、Edge、Checkpointer？
LangGraph 把 Agent 画成一张「流程图（状态机）」： • 节点 Node = 干活的步骤（如「调工具」「做总结」）； • 边 Edge = 下一步往哪走（还能根据条件分叉或绕圈）； • State = 所有节点共享的一块「公共白板」，记当前进展； • Checkpointer = 把白板存盘，支持断点恢复和多轮对话。 就像工厂流水线：工位（Node）在共享看板（State）上更新进度，传送带（Edge）决定流向，下班前拍张照（Checkpointer）明天接着干。
面试怎么答（技术内核）
  • StateGraph： 显式状态机（图/DAG），把控制流画出来，看得见、好调试。
  • Node： 修改 State 的函数（一个工位干一件事）。
  • Edge： 定义流转，含 conditional_edges 实现循环 / 分支（这是它比线性 Chain 强的地方）。
  • State： 跨节点共享内存（TypedDict），每步被节点「局部更新」。
  • Checkpointer： 持久化状态，支持断点恢复 / 线程 / 多轮对话。
避坑 / 拓展
  • 和 LangChain 区别（常考）： LangChain 链式线性、无原生状态/循环；LangGraph 支持循环/分支/并行 + 原生 checkpoint + HITL，适合复杂生产工作流。
  • 用图编排 = 把控制流显式化，便于可视化/调试/持久化/人机介入。

🔑 一句话记住：LangGraph=流程图状态机：Node 干活、Edge 指路、State 共享、Checkpointer 存盘。

💻 深度版 · 可运行伪代码

    log: list

    return {"n": state["n"] + 1, "log": state["log"] + ["step"]}

22为什么用「图」编排？State 怎么流转？
用「图」来编排，等于把控制流画出来——节点是能力、边是条件流转。好处是看得见、好调试、能存盘恢复、能随时让人介入。State 每走一步就被节点「局部更新」一次（像白板上贴一张新便利贴），所有节点都能看到最新进展，不会被覆盖丢信息。
面试怎么答（技术内核）
  • 图的价值： 把控制流显式化——节点=能力、边=条件流转，便于可视化/调试/持久化/人机介入。
  • State 流转： 每步被节点返回的部分更新（reduce），所有节点共享同一份 State，不会互相覆盖。
  • 适合场景： 需要循环（反思重试）、分支（路由）、多 Agent（Supervisor 派发）。
避坑 / 拓展
  • 别为用图而用图： 简单线性任务用 prompt chaining 就够，上图反而增加复杂度。
  • 图的边际收益在「复杂 + 需要可恢复/可介入」时才明显，和 LangGraph 的 Checkpointer 配合才发挥价值。

🔑 一句话记住：图编排=把流程画出来好调试可恢复；State 每步局部更新共享。

24长上下文 / 上下文窗口爆炸怎么处理？
聊久了、工具返回多了，上下文就「爆仓」（像电脑内存满了卡死）。解法：把历史压成摘要（用个小模型提炼「关键事实/决策」）、滑动窗口只留近期、需要啥再检索啥（检索式记忆）、多 Agent 各管各的局部上下文、工具结果只留结论不要全量（比如工具返回 1 万字，只存「查到 3 条相关订单」这个结论）。
面试怎么答（技术内核）
  • 摘要压缩： 用专用小模型把历史压成「关键事实/事件/决策」，丢掉闲聊细节。
  • 滑动窗口： 只保留近期若干轮，旧的不进上下文。
  • 检索式记忆： 只取相关片段进上下文，不一次性全装。
  • 上下文隔离： 多 Agent 各持局部上下文，互不污染。
  • 工具结果只留结论： 返回长就提炼成结论再写回 State。
避坑 / 拓展
  • 压缩会丢细节： 要评估退化点（在哪一轮开始掉质量），别压太狠把关键信息压没了。
  • Claude Code / OpenCode 用 read-only 子 Agent 取信息回传主 Agent，避免主上下文被撑爆——这是个很实用的工程模式。

🔑 一句话记住：上下文爆仓：摘要压缩+滑动窗口+检索记忆+只留结论。

25工具调用失败 / 外部 API 超时 / 异常怎么处理？
工具也会挂：API 超时、返回 500、参数错。处理原则分两类—— • 能重试的（超时、5xx 服务器错）：退避重试几次； • 不能重试的（4xx 参数错）：别硬重试，改参数或换工具； 有备胎数据源就切换；让 Agent 反思后改参数重调；实在不行兜底回复（「暂时查不到，稍后再试」）。
面试怎么答（技术内核）
  • 重试 + 退避： 指数退避，设 max_retry，避免无限循环把服务打挂。
  • 区分可重试 vs 不可重试： 超时/5xx 可重试；4xx 参数错误应改参数而非重试（重试也是同样错）。
  • 降级 / 替换： 有备用数据源就切换；让 Agent Reflection 改参数重调。
  • 兜底回复 + 结构化错误： 多 Agent 时子 Agent 失败要返回结构化错误给主控，主控决定重试/绕过/转人工；超时熔断。
避坑 / 拓展
  • 给工具加「使用说明 + 边界案例」 提升一次成功率，比事后重试更省事。
  • 重试要带 jitter（随机抖动），避免大量请求同时重试把下游打雪崩。

🔑 一句话记住：工具挂了：能重试的退避重试，参数错就改参，有备胎就切换。

26什么是 Reflection（反思）？自我批评如何提升质量？
Reflection 就是让 Agent「做完自己当评委」。产出后对照评分标准自我评审，发现毛病就改了重来，可多轮。常用于写代码、写长文——就像你写完方案自己读一遍挑刺，再改一版，质量明显上去。配合 evaluator-optimizer 工作流：一个负责生成、一个负责评估反馈。
面试怎么答（技术内核）
  • 机制： Agent 在产出后自我评审（对照 rubric），发现问题则修订重生成；可多轮迭代。常用于写代码、长文、答案质量。
  • evaluator-optimizer 工作流： 一个生成、一个评估反馈，形成「生成→评→改」闭环。
  • 独立 critic Agent： 让另一个 Agent 当评委，且不该看作者私有推理，避免 rubber-stamp（敷衍式点赞——看着像评了其实没认真看）。
避坑 / 拓展
  • 会倍增 token：只在「质量提升能抵消成本」时用（如代码、长文），别给每次闲聊都加反思。
  • Reflection 和 Plan / ReAct 常组合：先计划、边做边想、做完反思。能覆盖大多数复杂任务。

🔑 一句话记住：Reflection=做完自己当评委挑刺再改；质量敏感场景必用。

27如何做流式输出（streaming）？SSE / WebSocket？
用户不想等 Agent 憋半天。流式输出就是让 Agent「边想边吐」——先用 SSE 或 WebSocket 把 token/中间事件一点点推到前端，前端做「思考中…」占位和增量渲染，长任务还能显示进度（像 ChatGPT 一个字一个字蹦）。这样用户感觉「它在动」，体验好很多。
面试怎么答（技术内核）
  • 机制： Agent 逐步产出 token/事件，用 SSE（text/event-stream）或 WebSocket 推前端；后端用 async generator 逐块 yield；中间工具调用也以事件流暴露（如「正在调用搜索…」）。
  • SSE vs WebSocket： SSE 单向（服务器→浏览器）、基于 HTTP，简单够用，最常用；WebSocket 双向、适合需要前端往回发指令的场景。
  • 长任务进度： 可用 LangGraph stream_mode 或 A2A 的 tasks/sendSubscribe（SSE）拿进度事件。
避坑 / 拓展
  • 前端做「思考中」占位 + 增量渲染，别等全部生成完才显示。
  • 注意断线重连续传：网络抖断后能续上，别让用户重发整个请求。

🔑 一句话记住：流式=边想边吐；SSE 单向最常用，长任务显示进度。

28高并发 / 限速场景（如 10 万 QPS）怎么设计 Agent？
真上生产要扛量（比如 10 万 QPS，双十一级流量）。核心思路像开连锁店： • 无状态 + 水平扩展：每家店（实例）都能接客，忙了就多开几家； • 排队 + 限流：门口发号（令牌桶），满员就排队或拒客，别压垮后厨； • 推理批处理：vLLM 的 continuous batching 把多个请求凑一批算，省 GPU； • 缓存 + 降级：热门答案直接返缓存，超载就简化流程或转人工；租户隔离防一家挤垮全场。
面试怎么答（技术内核）
  • 无状态化 + 水平扩展： 实例随负载伸缩，请求可落到任意实例（状态放外部如 Redis/DB）。
  • 请求队列 + 令牌桶限流： 保护后端不被打爆，超阈值排队或快速失败。
  • 模型推理批处理： continuous batching（vLLM）提升 GPU 利用率。
  • 结果缓存 + 降级策略： 超载时简化流程 / 转人工；隔离租户避免互相影响。
避坑 / 拓展
  • 多 Agent 编排有协调瓶颈，可用消息总线解耦，别让主管 Agent 成为单点。
  • 企业级常考三板斧： 可复现性 / 限流 / 降级——这三点能讲清，高并发题就稳了。
  • 并发下 trace / 成本监控不能丢，否则扛住了量却不知道哪步出问题。

🔑 一句话记住：高并发：无状态扩实例+限流+批处理+缓存降级+租户隔离。

29你做过最复杂的 Agent 项目？最大难点？怎么解决？
这题考你「是不是真做过」，编不出来。用 STAR 法则讲：什么场景（Situation）、你啥角色（Task）、怎么行动（Action）、最后结果（Result）。重点不是项目多炫，而是你能说清「最难的点怎么定位、怎么解决、量化结果」——比如「多 Agent 上下文不一致，我用全局状态管理器 + 任务依赖图解决，延迟降了 40%、成功率从 82% 提到 95%」。

30Agent 落地企业如何保证数据安全和合规（PII、私有化）？
Agent 接入企业数据，安全是底线。就像让实习生进公司： • 敏感信息分级脱敏：工资、身份证这类 PII 先遮掉再进模型； • 能私有化就私有化：模型和数据都在自己机房，不出公网； • 所有工具调用留审计日志：谁调了啥、改了啥，可追溯； • 写操作必须显式授权：不能 Agent 自作主张删库； • 防提示注入 + 保留人工兜底 + 全链路溯源。
面试怎么答（技术内核）
  • 数据分级与脱敏： PII 检测 / 遮蔽，敏感字段不进模型或做假名化。
  • 私有化 / 隔离部署： 模型和数据不出企业边界，降低泄露面。
  • RBAC + 工具调用审计日志： 权限网关 + 安全沙箱，每次调用可追溯。
  • Guardrails 输出过滤 + 提示注入防护： 过滤有害输出、防外部 prompt 操控 Agent。
  • 保留人工兜底与全链路溯源： 高风险动作可介入，任何结果能追到来源。
避坑 / 拓展
  • 重点： MCP Server 暴露 DB 仍需自己的连接串 / 权限 / 审计——协议不替你做安全，别以为接了 MCP 就安全了。
  • 红蓝对抗 + 内容风控常态化：定期攻击测试你的 Agent，别上线才想安全。

🔑 一句话记住：企业安全底线：脱敏+私有化+审计+授权+防注入+可溯源。
